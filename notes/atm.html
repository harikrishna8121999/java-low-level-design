Design an ATM

Medium Java ~25 min read Code: org.nailyourinterview.lld.atm

A user inserts a card, enters a PIN, picks “withdraw” and types an amount. The ATM checks its own cash, the account balance and the notes it holds, then pays out in ₹2000, ₹500 and ₹100 notes.

This question tests two patterns. The State pattern controls the session: the same button does different things before and after the PIN. Chain of Responsibility splits the amount into notes: each dispenser takes what it can and passes the rest on.

Every LLD answer follows the same 5 steps. Requirement gathering splits into 3 buckets: extensibility, dynamic input and high traffic. Click a step to jump to it.

    1.2 Core functional requirements

    • Insert a card. Only one card at a time.
    • Enter the PIN. Wrong PIN: stay and ask again.
    • Select an option (withdraw).
    • Withdraw an amount. Reject if the ATM has too little cash, the account has too little balance, or the notes cannot make the amount.
    • Pay out with the largest notes first. Update the note counts, the ATM cash and the account balance.
    • Eject the card at any time, and after every withdrawal.

    1.4 Dynamic (user input)

    Nothing about the card, the account or the cash is hard-coded in the ATM. It comes in at runtime:

    • Machines and their notes: new ATM("ATM2", 0, 2, 5) → ₹2000 × 0, ₹500 × 2, ₹100 × 5, saved with atmRepository.save(atm).
    • Cards and accounts: new Card("CARD123", "1234", new Account("ACC123", 5000)).
    • User input: insertCard(card), enterPin("1234"), selectOption("WITHDRAW"), dispenseCash(1410), in any order.
    Validate the inputThe code does not check the amount. dispenseCash(-500) passes every check and adds ₹500 to the account (try it in the simulator). dispenseCash(0) prints “Cash dispensed: 0”. Reject amount <= 0 and amount % 100 != 0 before any other check. The PIN is a free String; check that it has 4 digits. The option string is ignored: any value means “withdraw”.

    1.5 High traffic (concurrency)

    One ATM: not needed. One physical machine serves one card at a time. All calls come from one keypad, one after another.

    The account: needed. One account is shared by every ATM, the mobile app and a second card on a joint account. DispenseCashState reads the balance, checks it, then writes balance − amount. Two ATMs that run this at the same moment can both pass the check: a classic check-then-act race. Say this out loud. The fix lives in the bank, not the ATM:

    • Debit in one atomic step: UPDATE account SET balance = balance - ? WHERE id = ? AND balance >= ?, or a lock per account.
    • Debit before the notes come out. If the notes jam, reverse the debit.
    • Use an idempotency key per transaction, so a retry after a network timeout does not debit twice.

    1.6 Non-functional requirements

    • Correct money — never pay without a debit, never debit without paying.
    • Secure — the PIN is checked by the bank, not compared in plain text on the ATM.
    • Readable — no big switch (status) in every method.
    • Extensible — a new note, state or option is a new class.
    Interview tipName the two patterns early: “State for the session, Chain of Responsibility for the notes.” Then draw the state diagram. The classes follow from it.

    2Core entities + breakdown

    Read the requirements again. Underline the nouns. Most nouns become classes. Verbs become methods.

    A user inserts a card linked to an account with a balance. The ATM holds a count of ₹2000, ₹500 and ₹100 notes. Many ATMs live in a repository. The ATM is idle, has a card inserted, is authenticated, or is dispensing cash. Each note dispenser pays what it can and passes the rest to the next one.

    Two sentences carry the design. “Idle … dispensing cash” are states, so each one becomes a class. “Passes the rest to the next one” is a chain, so each note type becomes a handler.

    EntityTypeResponsibility
    ATMMachineService / contextHolds the ATM data, the current card and the current state. Forwards every user action to the state.
    ATMStateInterfaceinsertCard, enterPin, selectOption, dispenseCash, ejectCard, getStatus.
    IdleState / CardInsertedState / AuthenticatedState / DispenseCashStateStateOne class per state. Does the work for that state and moves the machine to the next one.
    CashDispenserInterface (handler)setNextDispenser, canDispense, dispense.
    TwoThousand / FiveHundred / OneHundredDispenserHandlerTake as many of its notes as possible; pass the rest to next.

    Card / AccountModelCard number, PIN, account. Account number and balance.

    Common mistakeDo not put the note logic inside DispenseCashState as if (amount >= 2000) … if (amount >= 500) …. A new note then edits the state class. And do not write if (status == IDLE) … in every method of ATMMachine: 4 states × 5 actions = 20 branches.

    5Working code

    Build bottom-up: enum and models, then the repository, then the note chain, then the states, then ATMMachine. The code uses Lombok (@Getter, @Setter, @AllArgsConstructor) to remove boilerplate.

    5.1 Enum and models

    enums/ATMStatus.java · model/Account.java · model/Card.java · model/ATM.java
    public enum ATMStatus {
    IDLE, CARD_INSERTED, AUTHENTICATED, DISPENSE_CASH,
}

@Getter
@AllArgsConstructor
public class Account {
    private final String accountNumber;
    @Setter private double balance;
}

@Getter
@AllArgsConstructor
public class Card {
    private final String cardNumber;
    private final String pin;
    private final Account account;
}

@Getter
public class ATM {
    private final String id;
    @Setter private ATMStatus status;
    @Setter private double cashAvailable;

    @Setter private int twoThousandCount;
    @Setter private int fiveHundredCount;
    @Setter private int oneHundredCount;

    public ATM(String id, int twoThousandCount, int fiveHundredCount, int oneHundredCount) {
        this.id = id;
        this.cashAvailable = 2000 * twoThousandCount + 500 * fiveHundredCount + 100 * oneHundredCount;
        this.status = ATMStatus.IDLE;
        this.twoThousandCount = twoThousandCount;
        this.fiveHundredCount = fiveHundredCount;
        this.oneHundredCount = oneHundredCount;
    }
}

    ATM is plain data: no rules live here. Two weak points: cashAvailable repeats what the note counts already say, so the two can drift apart; and money is a double. Use long paise and compute the total from the counts.

    repository/ATMRepository.java

    An in-memory stand-in for a database. Swap it for a JDBC or JPA class later; the machine does not change.

    5.3 CashDispenser — the chain

    cor/CashDispenser.java · cor/TwoThousandDispenser.java · cor/OneHundredDispenser.java · cor/CashDispenserChainBuilder.java
    public interface CashDispenser {
    void setNextDispenser(CashDispenser next);
    boolean canDispense(ATM atm, int amount);
    void dispense(ATM atm, int amount);
}

public class TwoThousandDispenser implements CashDispenser {   // FiveHundredDispenser is the same with 500
    private CashDispenser next;

    @Override
    public void setNextDispenser(CashDispenser next) { this.next = next; }

    @Override
    public boolean canDispense(ATM atm, int amount) {
        int count = atm.getTwoThousandCount();
        int notes = Math.min(amount / 2000, count);              // as many as we need and have
        int remainder = amount - notes * 2000;
        return remainder == 0 || (next != null && next.canDispense(atm, remainder));
    }

    @Override
    public void dispense(ATM atm, int amount) {
        int count = atm.getTwoThousandCount();
        int notes = Math.min(amount / 2000, count);
        atm.setTwoThousandCount(count - notes);

        int remainder = amount - notes * 2000;
        if (notes > 0) System.out.println("Dispensed " + notes + " x 2000 notes");

        if (remainder > 0 && next != null) {
            next.dispense(atm, remainder);                       // pass the rest down the chain
        }
    }
}

public class OneHundredDispenser implements CashDispenser {    // the end of the chain
    private CashDispenser next;

    @Override
    public void setNextDispenser(CashDispenser next) { this.next = next; }

    @Override
    public boolean canDispense(ATM atm, int amount) {
        int notes = Math.min(amount / 100, atm.getOneHundredCount());
        return amount - notes * 100 == 0;                        // nobody left to pass to
    }

    @Override
    public void dispense(ATM atm, int amount) {
        int availableNotes = atm.getOneHundredCount();
        int notes = Math.min(amount / 100, availableNotes);
        atm.setOneHundredCount(availableNotes - notes);
        if (notes > 0) System.out.println("Dispensed " + notes + " x ₹100 notes");
    }
}

public class CashDispenserChainBuilder {
    public static CashDispenser buildChain() {
        CashDispenser d1 = new TwoThousandDispenser();
        CashDispenser d2 = new FiveHundredDispenser();
        CashDispenser d3 = new OneHundredDispenser();
        d1.setNextDispenser(d2);
        d2.setNextDispenser(d3);
        return d1;                                               // the head: ₹2000
    }
}

    Two passes. canDispense is a dry run: it changes nothing. dispense repeats the same maths and takes the notes. So the ATM never pays half an amount. Is greedy safe? Here, yes: 100 divides 500 and 500 divides 2000, so “largest first” always finds an answer if one exists. Add a ₹200 note and it breaks: ₹600 from {₹500 × 1, ₹200 × 3} — greedy takes ₹500 and is stuck with ₹100. Then you need a search (see §7).

    5.5 IdleState and CardInsertedState

    state/IdleState.java · state/CardInsertedState.java
    @AllArgsConstructor
public class IdleState implements ATMState {
    private final ATMMachine atmMachine;

    @Override
    public void insertCard(Card card) {
        atmMachine.setCurrentCard(card);
        System.out.println("Card inserted.");
        atmMachine.setState(new CardInsertedState(atmMachine));   // IDLE → CARD_INSERTED
    }

    @Override public void enterPin(String pin) { System.out.println("No card inserted."); }
    @Override public void selectOption(String option) { System.out.println("No card inserted."); }
    @Override public void dispenseCash(int amount) { System.out.println("No card inserted."); }
    @Override public void ejectCard() { System.out.println("No card to eject."); }
    @Override public ATMStatus getStatus() { return ATMStatus.IDLE; }
}

@AllArgsConstructor
public class CardInsertedState implements ATMState {
    private final ATMMachine atmMachine;

    @Override
    public void enterPin(String pin) {
        if (atmMachine.getCurrentCard().getPin().equals(pin)) {
            System.out.println("PIN correct. Authenticated.");
            atmMachine.setState(new AuthenticatedState(atmMachine));  // → AUTHENTICATED
        } else {
            System.out.println("Invalid PIN.");                       // stay; no retry limit
        }
    }

    @Override
    public void ejectCard() {
        atmMachine.setCurrentCard(null);
        System.out.println("Card ejected.");
        atmMachine.setState(new IdleState(atmMachine));               // → IDLE
    }

    @Override public void insertCard(Card card) { System.out.println("Card already inserted."); }
    @Override public void selectOption(String option) { System.out.println("Enter PIN first."); }
    @Override public void dispenseCash(int amount) { System.out.println("Enter PIN before dispensing."); }
    @Override public ATMStatus getStatus() { return ATMStatus.CARD_INSERTED; }
}

    option is ignored: every option means withdraw. This is the hook for balance, deposit and transfer (see §7).

    5.7 DispenseCashState — the busy one

    state/DispenseCashState.java
    @AllArgsConstructor
public class DispenseCashState implements ATMState {
    private final ATMMachine atmMachine;
    private final CashDispenser chain = CashDispenserChainBuilder.buildChain();

    @Override
    public void dispenseCash(int amount) {
        double atmBalance = atmMachine.getAtm().getCashAvailable();
        double accountBalance = atmMachine.getCurrentCard().getAccount().getBalance();

        if (amount > atmBalance) {
            System.out.println("ATM has insufficient cash. Cannot dispense " + amount);
            ejectCard();
            return;
        }
        if (amount > accountBalance) {
            System.out.println("Insufficient account balance.");
            ejectCard();
            return;
        }

        // Now check if note combination is possible
        if (chain.canDispense(atmMachine.getAtm(), amount)) {
            chain.dispense(atmMachine.getAtm(), amount);

            // Deduct from ATM cash & account balance
            atmMachine.getAtm().setCashAvailable(atmBalance - amount);
            atmMachine.getCurrentCard().getAccount().setBalance(accountBalance - amount);

            ejectCard();
            System.out.println("Cash dispensed: " + amount);
        } else {
            System.out.println("Cannot dispense requested amount with available denominations.");
            ejectCard();
        }
    }

    @Override
    public void ejectCard() {
        atmMachine.setCurrentCard(null);
        System.out.println("Card ejected.");
        atmMachine.setState(new IdleState(atmMachine)); // use factory
    }

    @Override public void insertCard(Card card) { System.out.println("Transaction in progress. Cannot insert another card."); }
    @Override public void enterPin(String pin) { System.out.println("Already authenticated."); }
    @Override public void selectOption(String option) { System.out.println("Option already selected."); }
    @Override public ATMStatus getStatus() { return ATMStatus.DISPENSE_CASH; }
}

    The state does the money checks; the chain does the notes. Lombok’s @AllArgsConstructor skips chain because it is final and already set. Three problems to raise: no check for amount <= 0; the balance is read, checked and written in three steps (a race across ATMs); and “Card ejected.” prints before “Cash dispensed”. All three are in the cheat sheet with fixes.

    5.8 ATMStateFactory

    factory/ATMStateFactory.java
    public class ATMStateFactory {
    public static ATMState getState(ATMStatus status, ATMMachine machine) {
        return switch (status) {
            case IDLE -> new IdleState(machine);
            case CARD_INSERTED -> new CardInsertedState(machine);
            case AUTHENTICATED -> new AuthenticatedState(machine);
            case DISPENSE_CASH -> new DispenseCashState(machine);
            default -> throw new IllegalArgumentException("Unknown ATM status: " + status);
        };
    }
}

    The factory maps the stored status (data) back to a state object (behaviour). It runs only at start-up. The states still use new for each transition. Risk: if an ATM was saved as DISPENSE_CASH, the machine restarts there with currentCard == null, and the next dispenseCash throws a NullPointerException.

    5.9 ATMMachine — the context

    service/ATMMachine.java
    @Getter
public class ATMMachine {
    private final ATM atm;
    private ATMState state;
    private final ATMRepository atmRepository;
    @Setter private Card currentCard;

    public ATMMachine(String atmId, ATMRepository atmRepository) {
        this.atmRepository = atmRepository;
        this.atm = atmRepository.getById(atmId)
                .orElseThrow(() -> new RuntimeException("ATM not found"));
        this.state = ATMStateFactory.getState(atm.getStatus(), this);
    }

    // user actions: the current state decides what happens
    public void insertCard(Card card)       { state.insertCard(card); }
    public void enterPin(String pin)        { state.enterPin(pin); }
    public void selectOption(String option) { state.selectOption(option); }
    public void dispenseCash(int amount)    { state.dispenseCash(amount); }
    public void ejectCard()                 { state.ejectCard(); }

    public void setState(ATMState state) {
        this.state = state;
        this.atm.setStatus(state.getStatus());   // keep the stored status in step
        // persist the changes in db
    }
}

    The five user methods are one line each. That is the sign the State pattern is working. setState also copies the status into the ATM, so the repository always knows where each machine is.

    7Design patterns
    
  
    Be honest in the interview. Say which patterns the code uses and which ones you would add.
    
  
    
    
    State used
    ATMState + 4 classes. ATMMachine forwards each action to state. Each state picks the next one with setState(...).
    
    
    Chain of Responsibility used
    ₹2000 → ₹500 → ₹100. Each handler takes its notes and passes the rest. A new note is a new class plus one link.
    
    
    Factory used
    ATMStateFactory turns a stored ATMStatus into a state object at start-up.
    
    
    Repository used
    ATMRepository hides where ATMs are stored. Today a HashMap; later a database.
    
    
    Strategy / Command would add
    One Transaction class per option (withdraw, balance, deposit). selectOption picks one instead of ignoring the string.
    
    
    Facade over the bank would add
    BankService.verifyPin and debit. The ATM stops holding PINs and balances, and the debit becomes atomic.
    
    
    Observer would add
    Low note count → alert the cash-loading team. Removes System.out from the model.
    
    
    Big switch on status avoid
    switch (status) in every method. 4 states × 5 actions = 20 branches spread over one class.
    
  
    
  
    SOLID check
    
      
      
    • S — States handle the session, dispensers handle notes, the repository handles storage. But DispenseCashState also does the account debit; that belongs to a bank service.
      • 
      
    • O — A new note or a new state is a new class. A new action (e.g. checkBalance) touches the interface and all 4 states — the known cost of State.
      • 
      
    • L — Any ATMState can be the current state; any CashDispenser can sit in the chain.
      • 
      
    • I — Each state must implement all 5 actions, even ones it rejects. A default method that prints “not allowed” would cut the noise.
      • 
      
    • D — States depend on the concrete ATMMachine; DispenseCashState builds its own chain. Inject the chain to test it alone.
      • 
    
    
  
    
  
    Example: a safer dispenseCash
    

    DispenseCashState.dispenseCash() — fixed version (suggestion)
    @Override
public void dispenseCash(int amount) {
    if (amount <= 0 || amount % 100 != 0) {                 // 1. validate the input
        System.out.println("Enter a positive multiple of 100.");
        return;                                              //    stay: let the user retry
    }
    ATM atm = atmMachine.getAtm();
    if (!chain.canDispense(atm, amount)) {                   // 2. dry run on the notes
        System.out.println("Cannot dispense " + amount + " with available notes.");
        ejectCard();
        return;
    }
    String account = atmMachine.getCurrentCard().getAccount().getAccountNumber();
    if (!bank.debit(account, amount, txId)) {                // 3. atomic debit at the bank
        System.out.println("Insufficient account balance.");
        ejectCard();
        return;
    }
    try {
        chain.dispense(atm, amount);                         // 4. notes out
    } catch (RuntimeException jam) {
        bank.reverse(txId);                                  //    no notes → give the money back
        throw jam;
    }
    System.out.println("Cash dispensed: " + amount);         // 5. print, then eject
    ejectCard();
}
    
  
    Order matters: validate → check notes (no side effects) → debit (one atomic call, safe across ATMs) → pay → eject. bank and txId are the new parts. The ATM total is no longer stored, so step 2 also covers “ATM has too little cash”.
    

    

    



    

    
  
    8Similar problems
    
  
    A problem is similar only if the ATM model carries over: a self-service machine with a few clear states, one context object that forwards user actions to the current state, a check on the user or their money, and an item or cash out from a limited stock. The problems below share that skeleton. They are ranked by how much of this design you can reuse.
    

  
    The shared skeleton
    
    Machine (context) → current State · stock (notes, items) · money (account or cash box) · loop: action → current state checks → do the work → setState(next).
