Design an Inventory Management System

Medium Java ~25 min read Code: org.nailyourinterview.lld.inventory_management

A company keeps products in several warehouses. Stock comes in from suppliers, goes out for orders and moves between warehouses. When stock gets low, the system alerts a manager and can reorder by itself.

The question tests three decisions. Where does the quantity live? In the warehouse, per SKU — not in the product. Who reacts to low stock? A list of Observers, so a new reaction is a new class. How much to reorder? A swappable Strategy. Every movement also goes into an audit log.

Every LLD answer follows the same 5 steps. Requirement gathering splits into 3 buckets: extensibility, dynamic input and high traffic. Click a step to jump to it.

LLD interview flow — applied to Inventory Management

▶Try it first

    1.2 Core functional requirements

    • Keep a catalog of products and a list of warehouses.
    • Stock in: add N units of a SKU to a warehouse.
    • Stock out: remove N units. Refuse when the warehouse has fewer than N.
    • Transfer N units from one warehouse to another.
    • Query: stock of a SKU per warehouse and in total; a stock report.
    • Low stock: when stock drops to the reorder level, alert and reorder. The reorder quantity comes from a rule.
    • Audit log: one record per movement (type, SKU, from, to, quantity).
    • Reject bad input: unknown SKU, unknown warehouse, quantity ≤ 0, transfer to the same warehouse.

    1.4 Dynamic (user input)

    Nothing is hard-coded in the classes. It comes in at runtime:

    • Catalog and warehouses: addProduct(new Product("LAP-1", "Laptop", ELECTRONICS, 55000, 5)), addWarehouse(new Warehouse("BLR", "Bengaluru")).
    • Movements: addStock("BLR", "LAP-1", 12), removeStock(...), transfer("BLR", "DEL", "LAP-1", 10).
    • Reactions: addObserver(new LowStockAlert()).
    • Rule: replenisher.setStrategy(new TopUpStrategy(3)).
    Validate the inputThe service rejects an unknown SKU, an unknown warehouse, a quantity of 0 or less, and a transfer to the same warehouse. A stock-out larger than the stock fails and changes nothing. Each check prints one clear message and returns early.

    1.5 High traffic (concurrency)

    Needed. Many orders hit the same SKU at once. The classic bug is the oversell: two threads both read “3 left”, both take 3, stock goes to −3.

    • In this code: Warehouse.removeStock is synchronized. It checks and takes in one step and returns -1 when there is not enough. No caller can split the check from the take.
    • Not yet safe: the service uses a plain HashMap and ArrayList, and the transaction id is history.size() + 1. Under threads use ConcurrentHashMap, an AtomicInteger id and a concurrent queue for the log.
    • Transfer is two steps (take from A, add to B). For a moment the units are “in transit”. Accept that, or lock both warehouses in a fixed order (by id) to avoid deadlock.
    • At real scale the stock lives in a database. Use one conditional update: UPDATE stock SET qty = qty - ? WHERE wh = ? AND sku = ? AND qty >= ?. One row changed = success. Run observers from an event queue, not inside the order call.

    1.6 Non-functional requirements

    • Correct — stock never goes negative; no oversell.
    • Auditable — every movement has a record that never changes.
    • Fast reads — stock lookup is a map lookup, O(1).
    • Extensible — a new reorder rule or a new alert channel is one new class.
    Interview tipSay early: “Product is catalog data. Quantity is warehouse data.” Then the multi-warehouse questions answer themselves.

    2Core entities + breakdown

    Read the requirements again. Underline the nouns. Most nouns become classes. Verbs become methods.

    A company keeps products in several warehouses. Each warehouse holds a quantity per SKU. Staff add stock from a supplier, remove stock for an order and transfer stock. Each movement becomes a transaction in the log. When stock drops to the reorder level, an alert fires and a replenisher orders more, using a reorder rule.

    “Quantity” is not a class and not a field of Product: it is a Map<sku, Integer> inside Warehouse. “Supplier” and “order” are out of scope, so they are just the words "supplier" and "customer" in the log. “Alert” and “replenisher” both react to the same event, so they share one interface. “Reorder rule” changes, so it is an interface too.

    EntityTypeResponsibility

    WarehouseModelId, city and stock: Map<sku, qty>. removeStock checks and takes in one synchronized step.
    ProductModelSKU, name, category, price, reorder level. No quantity.
    StockTransactionValue objectOne movement: id, type, SKU, from, to, quantity. Never changes.
    StockObserverInterfaceonLowStock(warehouse, product, quantity).
    LowStockAlertObserverPrints the alert for the manager.
    AutoReplenisherObserverAsks its strategy how much to order, then calls addStock.

    Common mistakeProduct.quantity. It works for one warehouse and breaks at two: which warehouse does the number belong to? Keep the product as catalog data and store quantity per (warehouse, SKU).

    4Ship-order flow

    The core operation is removeStock: validate, take the stock in one atomic step, log it, and fire the low-stock event only when the stock crosses the reorder level.

    InventoryService.removeStock() flowchart
    Example: BLR has 9 laptops, level 5. Ship 5 → 4 left. 9 > 5 and 4 ≤ 5, so the alert fires and 20 are reordered (now 24). Ship 2 more → 22: no event.

    5Working code

    Build bottom-up: enums and Product, then Warehouse and StockTransaction, then the strategy and the observers, then InventoryService. The code uses Lombok (@Getter, @Setter, @AllArgsConstructor) to remove boilerplate.

    5.1 Enums and Product

    enums/Category.java · enums/TransactionType.java · model/Product.java
    public enum Category { ELECTRONICS, GROCERY, CLOTHING }

public enum TransactionType { STOCK_IN, STOCK_OUT, TRANSFER }

@Getter
@AllArgsConstructor
public class Product {
    private final String sku;
    private final String name;
    private final Category category;
    private final double price;
    private final int reorderLevel;   // at or below this, stock is low
}

    No quantity field. A product is the same in every warehouse; only the count differs.

    5.2 Warehouse — the stock and the lock

    model/Warehouse.java
    public class Warehouse {
    @Getter private final String id;
    @Getter private final String city;
    private final Map<String, Integer> stock = new HashMap<>();   // sku -> quantity

    public Warehouse(String id, String city) {
        this.id = id;
        this.city = city;
    }

    public synchronized int getQuantity(String sku) {
        return stock.getOrDefault(sku, 0);
    }

    public synchronized int addStock(String sku, int quantity) {
        return stock.merge(sku, quantity, Integer::sum);
    }

    // Check and take in one step, so two orders cannot take the same units.
    // Returns the quantity left, or -1 when there is not enough.
    public synchronized int removeStock(String sku, int quantity) {
        int have = getQuantity(sku);
        if (have < quantity) return -1;
        stock.put(sku, have - quantity);
        return have - quantity;
    }
}

    Why synchronized here? The check (have < quantity) and the take (put) must be one step. If the service called getQuantity and then a separate “set”, two threads could both pass the check. Why no @Getter on stock? A getter would hand out the live map, and anyone could change it without the lock. Why return the quantity left? The caller needs “before” and “after” for the low-stock check, and a second read could already be stale.

    5.4 ReplenishmentStrategy — how much to order?

    strategy/ReplenishmentStrategy.java · FixedQuantityStrategy.java · TopUpStrategy.java
    public interface ReplenishmentStrategy {
    // How many units to order when stock is low
    int reorderQuantity(Product product, int currentQuantity);
}

// Always order the same batch size
@AllArgsConstructor
public class FixedQuantityStrategy implements ReplenishmentStrategy {
    private final int quantity;

    @Override
    public int reorderQuantity(Product product, int currentQuantity) {
        return quantity;
    }
}

// Fill back up to factor x reorder level
@AllArgsConstructor
public class TopUpStrategy implements ReplenishmentStrategy {
    private final int factor;

    @Override
    public int reorderQuantity(Product product, int currentQuantity) {
        return product.getReorderLevel() * factor - currentQuantity;
    }
}

    Rice: level 30, 25 left. Fixed → 20 (now 45). Top-up ×3 → 90 − 25 = 65 (now 90). Same event, different rule, no change anywhere else.

    5.5 Observers — who reacts to low stock?

    observer/StockObserver.java · LowStockAlert.java · AutoReplenisher.java
    public interface StockObserver {
    void onLowStock(Warehouse warehouse, Product product, int quantity);
}

public class LowStockAlert implements StockObserver {
    @Override
    public void onLowStock(Warehouse warehouse, Product product, int quantity) {
        System.out.println("ALERT: " + product.getName() + " is low in " + warehouse.getId()
                + " (" + quantity + " left, reorder level " + product.getReorderLevel() + ")");
    }
}

// Orders new stock from the supplier when stock is low. The strategy decides how much.
@AllArgsConstructor
public class AutoReplenisher implements StockObserver {
    private final InventoryService inventory;
    @Setter private ReplenishmentStrategy strategy;

    @Override
    public void onLowStock(Warehouse warehouse, Product product, int quantity) {
        int amount = strategy.reorderQuantity(product, quantity);
        if (amount <= 0) return;
        System.out.println("Reorder " + amount + " x " + product.getSku() + " for " + warehouse.getId()
                + " (" + strategy.getClass().getSimpleName() + ")");
        inventory.addStock(warehouse.getId(), product.getSku(), amount);
    }
}

    Observer + Strategy together. The observer answers “when do we act?”; the strategy answers “how much?”. amount <= 0 guards a top-up rule when stock is already high.

    5.6 InventoryService — the entry point

    service/InventoryService.java (core methods)
    public class InventoryService {
    private final Map<String, Product> products = new HashMap<>();          // sku -> product
    private final Map<String, Warehouse> warehouses = new LinkedHashMap<>(); // id -> warehouse
    private final List<StockTransaction> history = new ArrayList<>();
    private final List<StockObserver> observers = new ArrayList<>();

    public void addStock(String warehouseId, String sku, int quantity) {
        Warehouse warehouse = findWarehouse(warehouseId);
        if (warehouse == null || findProduct(sku) == null || !isPositive(quantity)) return;

        int now = warehouse.addStock(sku, quantity);
        record(TransactionType.STOCK_IN, sku, "supplier", warehouseId, quantity);
        System.out.println("+" + quantity + " " + sku + " -> " + warehouseId + " (now " + now + ")");
    }

    public boolean removeStock(String warehouseId, String sku, int quantity) {
        Warehouse warehouse = findWarehouse(warehouseId);
        Product product = findProduct(sku);
        if (warehouse == null || product == null || !isPositive(quantity)) return false;

        int left = warehouse.removeStock(sku, quantity);
        if (left < 0) {
            System.out.println("Not enough " + sku + " in " + warehouseId + ": have "
                    + warehouse.getQuantity(sku) + ", need " + quantity + ".");
            return false;
        }
        record(TransactionType.STOCK_OUT, sku, warehouseId, "customer", quantity);
        System.out.println("-" + quantity + " " + sku + " <- " + warehouseId + " (now " + left + ")");
        checkLowStock(warehouse, product, left + quantity, left);
        return true;
    }

    public boolean transfer(String fromId, String toId, String sku, int quantity) {
        if (fromId.equals(toId)) { System.out.println("Source and target are the same warehouse."); return false; }
        Warehouse from = findWarehouse(fromId);
        Warehouse to = findWarehouse(toId);
        Product product = findProduct(sku);
        if (from == null || to == null || product == null || !isPositive(quantity)) return false;

        int left = from.removeStock(sku, quantity);
        if (left < 0) { System.out.println("Not enough " + sku + " in " + fromId + " to move " + quantity + "."); return false; }
        int now = to.addStock(sku, quantity);
        record(TransactionType.TRANSFER, sku, fromId, toId, quantity);
        checkLowStock(from, product, left + quantity, left);
        return true;
    }

    public int getTotalStock(String sku) {
        return warehouses.values().stream().mapToInt(w -> w.getQuantity(sku)).sum();
    }

    // Fire once, when the stock crosses the reorder level (not on every sale below it)
    private void checkLowStock(Warehouse warehouse, Product product, int before, int after) {
        int level = product.getReorderLevel();
        if (before > level && after <= level) {
            observers.forEach(o -> o.onLowStock(warehouse, product, after));
        }
    }

    private void record(TransactionType type, String sku, String from, String to, int quantity) {
        history.add(new StockTransaction(history.size() + 1, type, sku, from, to, quantity));
    }

    // addProduct, addWarehouse, addObserver, printStock, printHistory,
    // findWarehouse / findProduct / isPositive print the error and return null / false
}

    Why a crossing check? “Alert when stock ≤ level” fires on every sale below the line: 4 left, 3 left, 2 left — three alerts and three reorders. “Was above, now at or below” fires once. Why LinkedHashMap for warehouses? The report keeps the order they were added.

    7Design patterns
    
  
    Be honest in the interview. Say which patterns the code uses and which ones you would add.
    
  
    
    
    Observer used
    StockObserver with LowStockAlert and AutoReplenisher. The service fires one event; it does not know who listens.
    
    
    Strategy used
    ReplenishmentStrategy: FixedQuantityStrategy, TopUpStrategy. Swapped at runtime with setStrategy.
    
    
    Facade / service used
    InventoryService is the one entry point. Callers never touch a Warehouse map directly.
    
    
    Immutable log used
    StockTransaction has only final fields. The history is append-only — the base for audit and replay.
    
    
    Repository would add
    Move the maps behind ProductRepository / WarehouseRepository. The service then works with memory or a database.
    
    
    Factory would add
    ProductFactory.create(type, ...) once there are perishable or serial-numbered products.
    
    
    Command would add
    Each movement as a command with execute() / undo(). Gives undo and a queue for one writer thread.
    
    
    Singleton service avoid
    Tempting (“one inventory”), but it blocks tests and makes the replenisher's back-reference global. Create it once and pass it in.
    
  
    
  
    SOLID check
    
      
      
    • S — Warehouse: hold and lock stock. Service: validate, log, notify. Observer: react. Strategy: decide quantity.
      • 
      
    • O — A new reorder rule or alert channel is a new class. Reservations would edit Warehouse — the known weak spot.
      • 
      
    • L — Any ReplenishmentStrategy works in the replenisher; any StockObserver works in the service.
      • 
      
    • I — Both interfaces have one method.
      • 
      
    • D — The service depends on StockObserver; the replenisher on ReplenishmentStrategy. But the replenisher depends on the concrete InventoryService — an interface like StockReceiver would fix it.
      •
