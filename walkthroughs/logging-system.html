Design a Logging System

Medium Java ~20 min read Code: org.nailyourinterview.lld.logger

An application calls logger.error("Disk full"). The logger must send the line to the right places — console, file, later a server — in the right format, and it must stay fast and safe when many threads log at once.

The question tests three decisions. Who decides where a level goes? A chain of handlers, one per level. How do many outputs get the same line? Each handler keeps a list of appenders (Observer). How does the line look? Each appender has a swappable formatter (Strategy). One Singleton Logger is the entry point.

Every LLD answer follows the same 5 steps. Requirement gathering splits into 3 buckets: extensibility, dynamic input and high traffic. Click a step to jump to it.

LLD interview flow — applied to a Logging System

▶Try it first

    1.2 Core functional requirements
    
  
      
    
    • Log a message at a level: debug, info, warn, error, fatal.
      • 
    
    • Each log line has a level, the message text and a timestamp.
      • 
    
    • Send each level to its own list of outputs (appenders): console, file.
      • 
    
    • Each output formats the line with its own formatter: plain text or JSON.
      • 
    
    • Add an output to a level at runtime.
      • 
    
    • A level with no output prints nothing.
      • 
    
    • One logger instance for the whole application.
      •

    1.4 Dynamic (user input)
    
  
    Nothing about the routing is hard-coded in the handlers. It comes in at runtime:
    
  
      
    
    • Routing: LogHandlerConfiguration.addAppenderForLevel(LogLevel.ERROR, new FileAppender(new PlainTextFormatter(), "logs.txt")).
      • 
    
    • Format per output: the formatter object passed to each appender.
      • 
    
    • Each call: the level (by method) and the message text: logger.error("Oh no!").
      • 
  
    
  
    Validate the inputThe code does not check much. A bad file path throws RuntimeException when the FileAppender is made (fail fast — good). But a null message prints "null", and a TRACE message walks the whole chain and is dropped with no warning, because no handler accepts TRACE. Add a TRACE handler, or a fallback at the end of the chain.
    

  
    1.5 High traffic (concurrency)
    
  
    Needed. Every thread in the app logs. Two problems appear: lines that mix in the file, and callers that wait for the disk.
    
  
      
    
    • In this code: FileAppender.append is synchronized, so one whole line (write + newline + flush) goes out before the next starts. System.out.println is already synchronized inside the JDK.
      • 
    
    • Safe subscribe: each handler keeps its appenders in a CopyOnWriteArrayList. A thread can add an appender while others loop over the list — no ConcurrentModificationException.
      • 
    
    • Safe singleton: INSTANCE is created eagerly in a static field, so the JVM makes it once, thread-safe, with no lock.
      • 
    
    • Not yet fast: logging is synchronous. The caller waits for flush() on every line, and all threads queue on one lock. Fix: an AsyncAppender — callers put the message in a bounded BlockingQueue and return; one worker thread takes and writes, and flushes in batches. Decide what to do when the queue is full (block, or drop DEBUG first). Drain the queue in a shutdown hook.
      • 
  
    

  
    1.6 Non-functional requirements
    
  
      
    
    • Low latency — a log call must not slow the request much.
      • 
    
    • Thread-safe — no mixed lines, no lost lines.
      • 
    
    • Reliable — one broken output must not stop the others or crash the app.
      • 
    
    • Extensible — a new output or format is one new class.
      • 
    
    • Configurable — routing changes without a code change in the handlers.
      • 
  
    
  
    Interview tipSay early: “Three questions: which level (chain), which outputs (observers), which format (strategy).” Each one is one interface. The rest of the design follows.
    

    

    



    

    
  
    2Core entities + breakdown
    
  
    Read the requirements again. Underline the nouns. Most nouns become classes. Verbs become methods.
    
  
    
    The app calls one shared logger with a level and a message. The logger stamps the time and passes the message to a handler for its level. The handler sends it to every output (console, file) set for that level. Each output formats the line with its own format (plain text, JSON). A configuration decides which outputs each level has.
  
    
  
    “Output” becomes LogAppender (the usual Log4j word). “Format” becomes LogFormatter. “Handler” is one class per level, linked into a chain. “Message” plus level plus time become one value object, LogMessage, so every part of the pipeline gets the same thing.

    4Log-a-message flow
    
  
    The core operation is logger.error("…"): build the message, walk the chain until one handler says “mine”, then let every appender of that handler format and write the line.
    

    

    
  
    Logger.log() flowchart
    
    
  
    
  
    
  
    Example (Main's set-up): error("Oh no!") → DEBUG no → INFO no → WARN no → ERROR yes → 2 appenders: console prints the line, file writes it to logs.txt. warn("…") stops at WarnHandler, which has no appenders: nothing prints.
    

    

    



    

    
  
    5Working code
    
  
    Build bottom-up: LogLevel and LogMessage, then formatters, then appenders, then handlers and their configuration, then the Logger. The code uses Lombok (@Getter, @AllArgsConstructor, @RequiredArgsConstructor, @Setter) to remove boilerplate.
    

  
    5.1 LogLevel and LogMessage
    

    enums/LogLevel.java · model/LogMessage.java
    public enum LogLevel {
    TRACE, DEBUG, INFO, WARN, ERROR, FATAL
}

@AllArgsConstructor
@Getter
public class LogMessage {
    private LogLevel level;
    private String message;
    private long timestamp;   // epoch millis
}
    
  
    One object travels the whole pipeline. A new field (thread name, request id) is added here once, and every formatter can use it.
    

  
    5.2 Formatters — how a line looks (Strategy)
    

    formatter/LogFormatter.java · PlainTextFormatter.java · JsonFormatter.java
    public interface LogFormatter {
    String format(LogMessage message);
}

public class PlainTextFormatter implements LogFormatter {
    private static final DateTimeFormatter FORMATTER =
            DateTimeFormatter.ofPattern("yyyy-MM-dd HH:mm:ss");

    @Override
    public String format(LogMessage message) {
        String formattedTime = LocalDateTime.ofInstant(
                Instant.ofEpochMilli(message.getTimestamp()),
                ZoneId.systemDefault()
        ).format(FORMATTER);

        return String.format("%s [%s] - %s", formattedTime, message.getLevel(), message.getMessage());
    }
}

public class JsonFormatter implements LogFormatter {
    // same FORMATTER and formattedTime as above
    @Override
    public String format(LogMessage message) {
        ...
        return String.format("{\"timestamp\": %s, \"level\": \"%s\", \"message\": \"%s\"}",
                formattedTime, message.getLevel(), message.getMessage());
    }
}
    
  
    Why static final DateTimeFormatter? It is immutable and thread-safe, so all threads share one. (The old SimpleDateFormat is not thread-safe.) Bug: the JSON timestamp has no quotes and the message is not escaped, so the output is not valid JSON. See Traps.
    

  
    5.3 Appenders — where a line goes (Observer)
    

    appenders/LogAppender.java · ConsoleAppender.java · FileAppender.java
    public interface LogAppender {
    void append(LogMessage message);
}

@RequiredArgsConstructor
public class ConsoleAppender implements LogAppender {
    private final LogFormatter formatter;

    @Override
    public void append(LogMessage message) {
        System.out.println(formatter.format(message));
    }
}

public class FileAppender implements LogAppender {
    private final LogFormatter formatter;
    private final BufferedWriter writer;

    public FileAppender(LogFormatter formatter, String fileName) {
        this.formatter = formatter;
        try {
            this.writer = new BufferedWriter(new FileWriter(fileName, true));   // append mode
        } catch (IOException e) {
            throw new RuntimeException("Failed to open log file", e);
        }
    }

    @Override
    public synchronized void append(LogMessage message) {
        try {
            writer.write(formatter.format(message));
            writer.newLine();
            writer.flush();   // flush can be batched or delayed
        } catch (IOException e) {
            e.printStackTrace();
        }
    }

    public synchronized void close() {
        try {
            writer.close();
        } catch (IOException e) {
            e.printStackTrace();
        }
    }
}
    
  
    Why synchronized? write, newLine and flush are three calls. Without the lock, thread A's text and thread B's text can land on the same line. Why catch the IOException? A full disk must not crash the app that is only trying to log. Cost: flush() per line hits the disk every time — safe but slow.
    

  
    5.4 LogHandler — one link of the chain
    

    handlers/LogHandler.java · ErrorHandler.java (others are the same)
    public abstract class LogHandler {
    @Setter
    protected LogHandler next;
    protected final List<LogAppender> appenders = new CopyOnWriteArrayList<>();

    public void subscribe(LogAppender observer) {
        appenders.add(observer);
    }

    public void notifyObservers(LogMessage message) {
        for (LogAppender appender : appenders) {
            appender.append(message);
        }
    }

    public void handle(LogMessage message) {
        if (canHandle(message.getLevel())) {
            notifyObservers(message);
        }
        else if (next != null) {
            next.handle(message);
        }
    }

    protected abstract boolean canHandle(LogLevel level);
}

public class ErrorHandler extends LogHandler {
    @Override
    protected boolean canHandle(LogLevel level) {
        return level == LogLevel.ERROR;
    }
}
// DebugHandler, InfoHandler, WarnHandler, FatalHandler: same, with their own level
    
  
    Two patterns in one class. next + handle is the chain; appenders + subscribe + notifyObservers is the subject of an observer. Why CopyOnWriteArrayList? Logging reads the list all the time; subscribing is rare. Each write copies the array, so readers never lock and never see a half-changed list. Note: the match is exact (==), so a message stops at its own level and goes no further.
    

  
    5.5 LogHandlerConfiguration — build the chain, route the levels
    

    LogHandlerConfiguration.java
    public class LogHandlerConfiguration {

    private static final LogHandler debug = new DebugHandler();
    private static final LogHandler info = new InfoHandler();
    private static final LogHandler warn = new WarnHandler();
    private static final LogHandler error = new ErrorHandler();
    private static final LogHandler fatal = new FatalHandler();

    public static LogHandler build() {
        debug.setNext(info);
        info.setNext(warn);
        warn.setNext(error);
        error.setNext(fatal);

        return debug;
    }

    public static void addAppenderForLevel(LogLevel level, LogAppender appender) {
        switch (level) {
            case DEBUG -> debug.subscribe(appender);
            case INFO  -> info.subscribe(appender);
            case WARN  -> warn.subscribe(appender);
            case ERROR -> error.subscribe(appender);
            case FATAL -> fatal.subscribe(appender);
        }
    }
}
    
  
    The handlers are static, so the chain that the logger holds and the handlers that addAppenderForLevel changes are the same objects. That is why you can subscribe after the logger is created. The price is global mutable state; see Traps.
    

  
    5.6 Logger — the Singleton entry point
    

    Logger.java
    class Logger {
    private static final Logger INSTANCE = new Logger();

    private final LogHandler handlerChain;

    private Logger() {
        handlerChain = LogHandlerConfiguration.build();
    }

    public static Logger getInstance() {
        return INSTANCE;
    }

    public void log(LogLevel level, String message) {
        LogMessage msg = new LogMessage(level, message, System.currentTimeMillis());
        handlerChain.handle(msg);
    }

    public void debug(String msg) { log(LogLevel.DEBUG, msg); }
    public void info(String msg)  { log(LogLevel.INFO, msg); }
    public void warn(String msg)  { log(LogLevel.WARN, msg); }
    public void error(String msg) { log(LogLevel.ERROR, msg); }
    public void fatal(String msg) { log(LogLevel.FATAL, msg); }
}
    
  
    Eager singleton. The JVM runs the static initialiser once, under its own class-init lock, so getInstance() needs no synchronized and no double-checked locking. Why stamp the time here? The time of the call is the time of the event; an async appender may write it much later.

    7Design patterns
    
  
    Be honest in the interview. Say which patterns the code uses and which ones you would add.
    
  
    
    
    Chain of Responsibility used
    LogHandler.next: DEBUG → INFO → WARN → ERROR → FATAL. Each link asks “mine?”; if not, it passes the message on.
    
    
    Observer used
    Each handler is a subject; LogAppenders subscribe to it. One message, many outputs, and the handler does not know their types.
    
    
    Strategy used
    LogFormatter: PlainTextFormatter, JsonFormatter. Each appender gets its own, so the file can be JSON while the console is plain.
    
    
    Singleton used
    Logger.INSTANCE, eager and thread-safe. Fair here: a logger is a true app-wide service with no business state.
    
    
    Decorator would add
    AsyncAppender(LogAppender inner): queue the message, return at once, and let a worker call inner.append. Works with any appender.
    
    
    Factory would add
    LoggerFactory.getLogger(name): one named logger per class, cached in a map, each with its own minimum level.
    
    
    Builder would add
    Build the configuration as an object (LoggingConfig.builder().route(ERROR, file).build()) or read it from a file, instead of static fields.
    
    
    Static mutable config avoid
    LogHandlerConfiguration's static handlers are global state: tests share them, and a second addAppenderForLevel with the same appender prints the line twice.
    
  
    
  
    SOLID check
    
      
      
    • S — Handler: pick the level. Appender: write. Formatter: shape the string. Logger: stamp the time and start the chain.
      • 
      
    • O — A new output or format is a new class. A new level edits the enum, build() and the switch — the known weak spot.
      • 
      
    • L — Any LogAppender works in any handler; any LogFormatter works in any appender.
      • 
      
    • I — LogAppender and LogFormatter have one method each.
      • 
      
    • D — Handlers depend on LogAppender; appenders on LogFormatter. But Logger calls the concrete, static LogHandlerConfiguration — pass a config object in instead.
      • 
    
    
  
    
  
    Example: a new appender, no change to the handlers
    

    appenders/AsyncAppender.java (would add)
    // Decorator: the caller only puts the message in a queue.
// One worker thread does the slow write.
public class AsyncAppender implements LogAppender {
    private final BlockingQueue<LogMessage> queue = new ArrayBlockingQueue<>(10_000);

    public AsyncAppender(LogAppender inner) {
        Thread worker = new Thread(() -> {
            try {
                while (true) inner.append(queue.take());
            } catch (InterruptedException e) {
                Thread.currentThread().interrupt();
            }
        }, "log-writer");
        worker.setDaemon(true);
        worker.start();
    }

    @Override
    public void append(LogMessage message) {
        if (!queue.offer(message)) {
            System.err.println("log queue full, dropped: " + message.getMessage());
        }
    }
}

LogHandlerConfiguration.addAppenderForLevel(LogLevel.ERROR,
        new AsyncAppender(new FileAppender(new JsonFormatter(), "errors.json")));
    
  
    No line in LogHandler or Logger changes. That is the Open/Closed principle at work. In production, also drain the queue in a shutdown hook so the last lines are not lost.
    

    

    



    

    
  
    8Similar problems
    
  
    A problem is similar only if the logger model carries over: a message with a severity or type, a routing step that picks the receivers, many output channels subscribed to a route, and a formatter per channel. The problems below share that skeleton. They are ranked by how much of this design you can reuse.
    

  
    The shared skeleton
    
    entry.log(level, text) → build a message → route.handle() pick by level / type → channels.forEach(append) → formatter.format() → write.
    
  
    

  
    
    
    ProblemReuse from LoggerNew part to learn
    
    
      
    Logging framework like Log4j / SLF4J
    closest    		All of it: levels, handlers, appenders, formatters, singleton entry.Named loggers in a hierarchy (com.app → com.app.db), a minimum level per logger, appender inheritance, async appenders, rolling files.
    
      
    Audit log / activity trackerMessage → route → appenders (DB, file) → formatter.Who did what to which record; never lose a line (write-ahead), never change one (append-only), search by user and time.
    
      
    Notification service (email, SMS, push)Event = message, priority = level, channels = appenders, templates = formatters.User preferences pick the channels; retries with backoff; rate limit per user; delivery status.
    
      
    Monitoring alert system (PagerDuty-style)Severity routing (P1 → phone + Slack, P3 → email), channel observers, message formats.Escalation over time if nobody acknowledges; dedupe of the same alert; on-call schedules.
    
      
    Pub-sub message broker (topic → subscribers)Subject + subscribed observers; fan-out of one message; thread-safe subscriber list.Topics instead of levels, consumer offsets, at-least-once delivery, back-pressure.
    
        
  
    

  
    Practice orderLogger (this) → Log4j-style framework (named loggers + thresholds + async) → Audit log (durability) → Notification service (preferences + retries) → Alert system (escalation) → Pub-sub broker (topics + offsets).
    

    

    



    

    
  
    9Revision cheat sheet
    
  
    Read top to bottom, in the order you speak in the interview. Then close your eyes and use the flip cards.
    

  
    
    In one breath
    A Singleton Logger stamps a LogMessage (level, text, time) and hands it to a chain of LogHandlers DEBUG → … → FATAL. The handler whose level matches notifies its LogAppenders (Observer): console, file. Each appender asks its LogFormatter (Strategy) for the string — plain text or JSON — and writes it; FileAppender.append is synchronized so lines never mix. LogHandlerConfiguration builds the chain and routes appenders to levels.

    // LogHandler: mine → notify appenders; else → pass on
void handle(LogMessage m) {
    if (canHandle(m.getLevel())) appenders.forEach(a -> a.append(m));
    else if (next != null) next.handle(m);
}

// Logger: stamp the time, start the chain
handlerChain.handle(new LogMessage(level, text, System.currentTimeMillis()));

// FileAppender: one whole line at a time
synchronized void append(LogMessage m) {
    writer.write(formatter.format(m)); writer.newLine(); writer.flush();

    Traps → fixes
    
  
    
    
      
    Exact match: canHandle is level == ERROR, so an ERROR never reaches the appenders of WARN or lower. Real loggers use “this level and above”.level.ordinal() >= min, and a handler both handles and passes on. With exact match only, a EnumMap<LogLevel, List<LogAppender>> is simpler than a chain
    
      
    TRACE is in the enum but has no handler: it walks the chain and is dropped with no warningAdd a TraceHandler, or a fallback at the end of the chain that reports unknown levels
    
      
    JsonFormatter writes the timestamp without quotes and does not escape " or \n in the message → invalid JSONQuote the timestamp and escape the text, or use Jackson / Gson
    
      
    Synchronous logging: the caller waits for flush() on every line, and all threads queue on one lockAsyncAppender decorator: bounded BlockingQueue + one worker, flush in batches
    
      
    FileAppender.close() is never called; with batched flushing the last lines are lost on exitRegister a shutdown hook that drains the queue and closes every appender
    
      
    One appender throws a RuntimeException → the loop in notifyObservers stops, and the next appenders never get the line (the exception can even reach the app)try/catch around each appender.append; report to System.err
    
      
    Static handlers in LogHandlerConfiguration = global mutable state; tests leak into each other; the same appender added twice prints twiceAn instance config passed to the logger; reject duplicates
    
      
    A new level needs edits in 3 places: enum, build(), switchOne generic LevelHandler(LogLevel); build the chain by looping over LogLevel.values()
    
      
    Logger is package-private, so code outside logger cannot use itMake the class public
    
      
    Two lines mix in the file under threadssynchronized append (done)
    
      
    Subscribe while another thread logs → ConcurrentModificationExceptionCopyOnWriteArrayList (done)
