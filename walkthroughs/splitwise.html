Design Splitwise

Hard Java ~25 min read Code: org.nailyourinterview.lld.splitwise

Friends share costs in a group. One person pays; the cost splits among some members — equally or by percentage. The app keeps track of who owes whom, and can simplify the debts so the group settles with fewer payments.

The question tests three decisions. How do you split? A Strategy per split type, picked by a factory. Where do balances live? One BalanceSheet per member per group, updated on both sides for every share. How do you simplify? Reduce everyone to one net number, then match the biggest creditor with the biggest debtor until all are zero.

Every LLD answer follows the same 5 steps. Requirement gathering splits into 3 buckets: extensibility, dynamic input and high traffic. Click a step to jump to it.

    1.2 Core functional requirements

    • Create a group with members; add a member later.
    • Add an expense: description, amount, payer, participants, split type (and percentages for a percentage split).
    • Split equally, or by percentage (the percentages must add up to 100).
    • Keep, per member: total paid, total own expense, and a balance with every other member.
    • Show each member's balances.
    • Simplify the debts of a group: same net amount per person, fewer payments.

    1.3 Extensibility (new features)

    1.4 Dynamic (user input)

    Nothing is hard-coded. Groups, members and expenses come in at runtime:

    • createGroup("Goa Trip", List.of(shubh, bob, tom)) returns the group id.
    • addExpense(groupId, "Lunch Day-1", 100, shubh, List.of(shubh, bob), SplitType.EQUAL, null).
    • Percentages: Map.of(shubh, 50.0, bob, 30.0, tom, 20.0) as the last argument.
    Validate the inputThe code checks two things: an unknown group id throws, and percentages must sum to exactly 100. It does not check that the payer and participants are members, that the amount is positive, or that the percentage map is present. An outsider makes getBalanceSheet() return null, so the call fails with a NullPointerException. See Traps → fixes.

    1.5 High traffic (concurrency)

    Needed, but per group. Many groups work in parallel, and they never touch each other. Inside one group, two members can add expenses at the same moment. The code is single-threaded: plain HashMap balances and += updates.

    • Race: two expenses both read Bob's balance with Tom, both add, one update is lost. Fix: lock per group (synchronized (group) around addExpense and simplifyDebts).
    • At real scale: store expenses as an append-only ledger in a database. Each expense and its splits go in one transaction. Balances are a derived table (or a cache) that you can rebuild from the ledger.
    • Double tap: send an idempotency key with “add expense”, so a retry does not add it twice.
    • Reads (open the app, see balances) far outnumber writes. Cache balances per group; invalidate on a new expense.

    1.6 Non-functional requirements

    • Correct money — the sum of all balances in a group is always 0. No lost cents.
    • Consistent — “A owes B 50” and “B gets 50 from A” always change together.
    • Fast reads — balances are kept up to date on write, not computed from all expenses on read.
    • Extensible — a new split type is one new class.
    Interview tipSay the invariant out loud: “For every share, the participant's balance goes down and the payer's goes up by the same amount. So each group sums to zero.” Simplification only works because of it.

    2Core entities + breakdown

    Read the requirements again. Underline the nouns. Most nouns become classes. Verbs become methods.

    Users form a group. A member pays an expense. The expense is split into shares by a split type. Each member has a balance sheet: what they paid, what they spent, and what they owe or get back from each other member. A member can simplify the group's debts.

    “Share” becomes Split (a user and an amount). “Split type” is an enum, and the way to split is a strategy. “Owe” and “get back” are not classes: they are the sign of one number in BalanceSheet.balances (negative = I owe, positive = I get back). Services hold the verbs: ExpenseService adds, BalanceSheetService updates, DebtSimplificationService simplifies, GroupService is the entry point.

    EntityTypeResponsibility
    UserModelId and name.
    GroupModelMembers, expenses, and one BalanceSheet per member.
    ExpenseModelDescription, amount, payer, list of splits, split type.
    SplitModelOne share: user + amount.
    BalanceSheetModeltotalPaid, totalExpense, balances: Map<User, Double> (+ get back, − owe).
    SplitStrategy → Equal, PercentageStrategysplit(amount, participants, metadata) → list of splits.
    SplitStrategyFactoryFactorySplitType → strategy.
    GroupServiceService (facade)Create groups, add members and expenses, simplify, print. Looks groups up in the repository.
    ExpenseServiceServiceSplit, build the Expense, store it, ask for the balance update.

    DebtSimplificationServiceServiceNet balances, then greedy matching with two heaps.

    Common mistakeKeeping only one global “debt list” of (from, to, amount) records and summing it on every read. It works, but every balance view scans every expense. Keep the running balance per pair, and keep the expenses as the history.

    4Simplify-debts flow

    Adding an expense is a straight line (split → store → update both sides). The interesting algorithm is simplifyDebts: turn many pairwise debts into one net number per person, then rebuild the debts with as few payments as the greedy rule finds.

    DebtSimplificationService.simplifyDebts() flowchart
    Main: Bob owes Shubh 50, Tom owes Bob 50. Net: Shubh +50, Bob 0, Tom −50. Bob is in no heap. One round: Shubh ↔ Tom, amount 50. Result: Tom owes Shubh 50 — one payment instead of two.

    5Working code

    Build bottom-up: the models, then the split strategies and factory, then BalanceSheet and Group, then the services. The code uses Lombok (@Getter, @AllArgsConstructor, @ToString) to remove boilerplate.

    5.2 SplitStrategy — how to split

    strategy/SplitStrategy.java · EqualSplitStrategy.java · PercentageSplitStrategy.java · factory/SplitStrategyFactory.java
    public interface SplitStrategy {
    List<Split> split(double totalAmount, List<User> participants, Map<User, Double> metadata);
}

public class EqualSplitStrategy implements SplitStrategy {
    public List<Split> split(double totalAmount, List<User> participants, Map<User, Double> metadata) {
        double share = totalAmount / participants.size();
        List<Split> splits = new ArrayList<>();
        for (User user : participants) {
            splits.add(new Split(user, share));
        }
        return splits;
    }
}

public class PercentageSplitStrategy implements SplitStrategy {
    public List<Split> split(double totalAmount, List<User> participants, Map<User, Double> metadata) {
        double totalPercent = metadata.values().stream().mapToDouble(Double::doubleValue).sum();
        if (totalPercent != 100.0) throw new IllegalArgumentException("Total percent should be 100");

        List<Split> splits = new ArrayList<>();
        for (User user : participants) {
            splits.add(new Split(user, totalAmount * metadata.getOrDefault(user, 0.0) / 100));
        }
        return splits;
    }
}

public class SplitStrategyFactory {
    public static SplitStrategy getStrategy(SplitType splitType) {
        return switch (splitType) {
            case EQUAL -> new EqualSplitStrategy();
            case PERCENTAGE -> new PercentageSplitStrategy();
        };
    }
}

    Why one signature with metadata? Every strategy fits one interface: equal ignores it, percentage reads percents, an exact split would read amounts. The cost: the map means different things per type, and nothing checks that the right one was passed. Two bugs: != 100.0 on doubles rejects valid input (0.1 + 64.1 + 35.8 = 99.99999999999999), and 100 / 3 gives 33.333… — not a real amount of money.

    5.3 BalanceSheet and Group

    model/BalanceSheet.java · model/Group.java
    @Getter
public class BalanceSheet {
    private double totalPaid = 0.0;
    private double totalExpense = 0.0;
    private final Map<User, Double> balances = new HashMap<>();   // + they owe me, - I owe them

    public void addTotalPaid(double amount) { this.totalPaid += amount; }
    public void addTotalExpense(double amount) { this.totalExpense += amount; }

    public void addBalance(User other, double amount) {
        balances.put(other, balances.getOrDefault(other, 0.0) + amount);
        if (Math.abs(balances.get(other)) < 1e-6) balances.remove(other);
    }

    public void clearBalances() { balances.clear(); }
    // print(User me) ...
}

@Getter
public class Group {
    private final String id;
    private final String name;
    private final List<User> members = new ArrayList<>();
    private final List<Expense> expenses = new ArrayList<>();
    private final Map<User, BalanceSheet> balanceSheets = new HashMap<>();

    public Group(String id, String name) { this.id = id; this.name = name; }

    public void addMember(User user) {
        members.add(user);
        balanceSheets.putIfAbsent(user, new BalanceSheet());
    }

    public void addExpense(Expense expense) { expenses.add(expense); }

    public BalanceSheet getBalanceSheet(User user) { return balanceSheets.get(user); }
}

    Why remove a balance near 0? A settled pair should disappear from the “you owe / you get” list, and doubles rarely land on exactly 0. Why a sheet per group? “Bob owes Tom 50 for Goa” and “Tom owes Bob 20 for rent” are separate stories; each group settles on its own.

    5.4 BalanceSheetService — both sides of each share

    service/BalanceSheetService.java
    public class BalanceSheetService {

    public void updateBalances(Group group, User paidBy, List<Split> splits) {
        double totalAmount = splits.stream().mapToDouble(Split::getAmount).sum();
        group.getBalanceSheet(paidBy).addTotalPaid(totalAmount);

        for (Split split : splits) {
            User user = split.getUser();
            double amt = split.getAmount();
            group.getBalanceSheet(user).addTotalExpense(amt);
            if (!user.equals(paidBy)) {
                group.getBalanceSheet(user).addBalance(paidBy, -amt);   // user owes payer
                group.getBalanceSheet(paidBy).addBalance(user, amt);    // payer gets back
            }
        }
    }
}

    The heart of the design. Every share changes two numbers by the same amount with opposite signs, so the whole group always sums to 0. The payer's own share counts as expense but creates no debt. Example: Shubh pays 90 for Shubh, Bob, Tom → Shubh paid 90, spent 30, gets 30 from Bob and 30 from Tom; Bob and Tom each owe Shubh 30.

    5.5 ExpenseService and GroupService

    service/ExpenseService.java · service/GroupService.java (core)
    @AllArgsConstructor
public class ExpenseService {
    private final BalanceSheetService balanceSheetService;

    public void addExpense(Group group, String description, double amount, User paidBy,
                           List<User> participants, SplitType splitType, Map<User, Double> metadata) {

        SplitStrategy strategy = SplitStrategyFactory.getStrategy(splitType);
        List<Split> splits = strategy.split(amount, participants, metadata);
        Expense expense = new Expense(description, amount, paidBy, splits, splitType);
        group.addExpense(expense);

        balanceSheetService.updateBalances(group, paidBy, splits);
    }
}

@AllArgsConstructor
public class GroupService {
    private final GroupRepository repo;
    private final ExpenseService expenseService;
    private final DebtSimplificationService simplifier;

    public String createGroup(String name, List<User> members) {
        String id = UUID.randomUUID().toString();
        Group g = new Group(id, name);
        members.forEach(g::addMember);
        repo.save(g);
        return id;
    }

    public void addExpense(String groupId, String description, double amount,
                           User paidBy, List<User> participants,
                           SplitType splitType, Map<User, Double> meta) {
        expenseService.addExpense(get(groupId), description, amount, paidBy, participants, splitType, meta);
    }

    public void simplifyDebts(String groupId) {
        simplifier.simplifyDebts(get(groupId));
    }

    private Group get(String id) {
        return repo.findById(id)
                .orElseThrow(() -> new IllegalArgumentException("Group not found: " + id));
    }
    // addMember, printBalances ...
}

    Why a separate GroupService? Callers use a group id; only this class knows the repository. ExpenseService gets a real Group and never does lookups. Order matters: split first. If the split throws (bad percentages), nothing is stored and no balance changes.

    5.6 DebtSimplificationService — fewer payments

    service/DebtSimplificationService.java
    public class DebtSimplificationService {

    public void simplifyDebts(Group group) {
        List<User> users = new ArrayList<>(group.getMembers());
        Map<User, BalanceSheet> sheets = group.getBalanceSheets();

        // Step 1: Calculate net balances for each user
        Map<User, Double> netBalances = new HashMap<>();
        for (User user : users) {
            double net = 0.0;
            for (double amount : sheets.get(user).getBalances().values()) net += amount;
            netBalances.put(user, net);
            sheets.get(user).clearBalances(); // Clear old balances before recomputing
        }

        // Step 2: Separate creditors and debtors
        PriorityQueue<User> creditors = new PriorityQueue<>((a, b) -> Double.compare(netBalances.get(b), netBalances.get(a)));
        PriorityQueue<User> debtors = new PriorityQueue<>((a, b) -> Double.compare(netBalances.get(a), netBalances.get(b)));
        for (User user : users) {
            double net = netBalances.get(user);
            if (net > 0) creditors.offer(user);
            else if (net < 0) debtors.offer(user);
        }

        // Step 3: Match debtors and creditors to settle debts
        while (!creditors.isEmpty() && !debtors.isEmpty()) {
            User creditor = creditors.poll();
            User debtor = debtors.poll();

            double creditAmount = netBalances.get(creditor);
            double debitAmount = netBalances.get(debtor);
            double settledAmount = Math.min(creditAmount, -debitAmount);

            sheets.get(creditor).addBalance(debtor, settledAmount);
            sheets.get(debtor).addBalance(creditor, -settledAmount);

            netBalances.put(creditor, creditAmount - settledAmount);
            netBalances.put(debtor, debitAmount + settledAmount);

            if (netBalances.get(creditor) > 0) creditors.offer(creditor);
            if (netBalances.get(debtor) < 0) debtors.offer(debtor);
        }
    }
}

    Why it works: who pays whom does not matter, only each person's net. Each round settles one side fully, so there are at most n − 1 payments. Why poll, change, then offer again? A PriorityQueue does not re-sort when a key changes; the user must leave the heap before its net changes. Honest limit: greedy is not always the minimum number of payments — that problem is NP-hard. Greedy is what Splitwise-style answers use.

    7Design patterns
    
  
    Be honest in the interview. Say which patterns the code uses and which ones you would add.
    
  
    
    
    Strategy used
    SplitStrategy with EqualSplitStrategy and PercentageSplitStrategy. ExpenseService does not know how a split is computed.
    
    
    Simple Factory used
    SplitStrategyFactory.getStrategy(SplitType). One switch maps the enum to a strategy.
    
    
    Repository used
    GroupRepository + InMemoryGroupRepository. A database version needs no service change.
    
    
    Service layer / facade used
    GroupService is the entry point; three smaller services each own one rule. Dependencies come in through constructors.
    
    
    Registry factory would add
    Map<SplitType, SplitStrategy> filled at start-up. A new split type then needs no factory edit, and strategies (they have no state) are reused.
    
    
    Command would add
    Each expense or payment as a command with apply() / revert(). Gives edit, delete and an audit trail.
    
    
    Observer would add
    ExpenseListeners: push a notification, update an activity feed, refresh a cache.
    
    
    double for money avoid
    33.333… is not money, and exact compares fail. Use long paise or BigDecimal. Also avoid a Singleton service: tests need fresh state.
    
  
    
  
    SOLID check
    
      
      
    • S — One rule per service: split, update balances, simplify, look up groups.
      • 
      
    • O — A new split type is a new class plus an enum value and a factory case — not fully closed. A registry fixes it.
      • 
      
    • L — Any SplitStrategy returns a list of splits; the rest of the code does not care which.
      • 
      
    • I — Interfaces are small (split; findById + save).
      • 
      
    • D — GroupService depends on GroupRepository, not the in-memory class. But ExpenseService calls the static factory directly, so a test cannot inject a fake strategy.
      • 
    
    
  
    
  
    Example: an exact split, plus a registry
    

    strategy/ExactSplitStrategy.java (would add)
    public class ExactSplitStrategy implements SplitStrategy {
    public List<Split> split(double totalAmount, List<User> participants, Map<User, Double> amounts) {
        double sum = participants.stream().mapToDouble(u -> amounts.getOrDefault(u, 0.0)).sum();
        if (Math.abs(sum - totalAmount) > 0.01)
            throw new IllegalArgumentException("Exact amounts add up to " + sum + ", not " + totalAmount);
        return participants.stream().map(u -> new Split(u, amounts.getOrDefault(u, 0.0))).toList();
    }
}

// Registry instead of a switch: add one line, touch nothing else
Map<SplitType, SplitStrategy> strategies = Map.of(
        SplitType.EQUAL, new EqualSplitStrategy(),
        SplitType.PERCENTAGE, new PercentageSplitStrategy(),
        SplitType.EXACT, new ExactSplitStrategy());
    
  
    BalanceSheetService and DebtSimplificationService do not change: they only see splits. Note the tolerance check (> 0.01) instead of !=.
    

    

    



    

    
  
    8Similar problems
    
  
    A problem is similar only if the shared-ledger model carries over: people, a payment that splits into shares, a running balance per pair that always sums to zero, and settling with as few transfers as possible. The problems below share that skeleton. They are ranked by how much of this design you can reuse.

// Simplify: net per user, then biggest creditor ↔ biggest debtor
while (!creditors.isEmpty() && !debtors.isEmpty()) {
    User c = creditors.poll(), d = debtors.poll();
    double x = Math.min(net.get(c), -net.get(d));
    sheet(c).addBalance(d, x);  sheet(d).addBalance(c, -x);
    net.put(c, net.get(c) - x); net.put(d, net.get(d) + x);
    if (net.get(c) > 0) creditors.offer(c);
    if (net.get(d) < 0) debtors.offer(d);
}
    
      
    
    
    
  
    

  
    Traps → fixes
    
  
    
    
      
    Payer or participant not in the group → getBalanceSheet() is null → NullPointerException (checked)Validate membership in ExpenseService; throw a clear error
    
      
    User has no equals / hashCode: a new User("u2", "Bob") is a different key → NPE (checked)@EqualsAndHashCode(of = "id"), or look users up by id
    
      
    totalPercent != 100.0 rejects 0.1 + 64.1 + 35.8 = 99.99999999999999 (checked)Math.abs(total - 100) < 0.01, or percent in basis points (int)
    
      
    double money: 100 / 3 = 33.333…, and cents driftlong paise; give the remainder paise to the first r people
    
      
    Percentage split with null map → NPE; percents for non-participants are summed but ignoredRequire the map; its keys must equal the participants
    
      
    No check for amount ≤ 0 or an empty participant list (equal split divides by 0)Validate before splitting
    
      
    simplifyDebts overwrites the pair balances; the original who-owes-whom is lostKeep raw balances; return the simplified list as a view
    
      
    @Getter on Group hands out the live members list; addMember twice adds a duplicateReturn an unmodifiable copy; use a LinkedHashSet
    
      
    “Non-Group Expenses” is a group, so one friend's balances are split across groupsA friend view that sums the pair over all groups
    
      
    Plain HashMap and +=: two expenses at once lose an updateLock per group, or one DB transaction per expense
    
      
    Greedy simplify is not always the minimum number of paymentsSay so: the exact problem is NP-hard; greedy gives ≤ n − 1
