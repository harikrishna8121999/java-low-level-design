Design a Parking Lot

Medium Java ~30 min read Code: org.nailyourinterview.lld.parking_lot

A parking lot has floors. Each floor has spots for bikes, cars or trucks. A vehicle enters at an entry gate and gets a ticket. At the exit gate the driver pays a fee, and the spot becomes free again.

This is the most common LLD question. It tests three things: a clean has-a tree (lot → floor → spot), Strategy for pricing and payment, and concurrency — many gates must not give the same spot to two cars.

Every LLD answer follows the same 5 steps. Requirement gathering splits into 3 buckets: extensibility, dynamic input and high traffic. Click a step to jump to it.

LLD interview flow — applied to Parking Lot

▶Try it first

Before you read the solution, spend 10–15 minutes on your own. Use paper. A wrong first attempt is fine — it makes the answer stick when you read it.

Park a few vehicles. Move the clock forward. Then click Exit on a spot and watch the fee. Try ⚡ Race: two bikes reach two gates at the same moment. The grey line under each log entry shows the method that does the work — ignore it for now.

    1.2 Core functional requirements

    • A lot has floors. A floor has spots. Each spot allows one VehicleType: BIKE, CAR or TRUCK.
    • Park: find a free spot of the same type, mark it occupied and issue a Ticket (id, entry time, vehicle, floor, spot).
    • If no spot is free, tell the driver.
    • Unpark: take the ticket id, exit time and payment mode. Calculate the fee. Take the payment. Free the spot. Close the ticket.
    • If the payment fails, the vehicle cannot exit.
    • Pricing: time-based (peak / non-peak per hour) or event-based (flat high rate per hour). It can change at runtime.
    • Payment: cash, UPI or card.

    1.3 Extensibility (new features)

    1.4 Dynamic (user input)

    Nothing about the layout is hard-coded in the lot. Main builds it at runtime and passes values in:

    • Floors and spots: lot.addFloor(floor), floor.addSpot(new ParkingSpot(id, type)).
    • Pricing from a string: PricingStrategyType.valueOf("EVENT_BASED") → factory → lot.setPricingStrategy(...).
    • Payment mode at the exit gate: unparkVehicle(ticketId, exitTime, PaymentMode.UPI).
    • Entry and exit times as text: DateTimeParser.parse("21 May 7:30 AM 2025"). Time is a parameter, not now(), so tests are easy.
    Validate the inputAn unknown pricing name makes valueOf throw. A duplicate spot id silently replaces the old spot in the map. An exit time before the entry time throws in TimeBasedPricing but gives a negative fee in EventBasedPricing — check it once, in ParkingLot.

    1.5 High traffic (concurrency)

    Needed. Many entry gates run at the same time. Two gates can see the same free spot. Without care, both cars get it.

    • Spot booking (done in the code): ParkingSpot.occupied is an AtomicBoolean. tryOccupy() calls compareAndSet(false, true). Only one thread wins. The loser goes on to the next spot. No lock on the whole lot.
    • Ticket map (gap): activeTickets is a plain HashMap, and many gates write to it. Use ConcurrentHashMap.
    • Double exit (gap): one ticket at two exit gates → both read it, both charge. Fix: activeTickets.remove(id) first. Only one thread gets the ticket back.
    • Floors map: filled once at start-up, then only read. Safe if setup ends before the gates open.
    • Singleton: eager static final INSTANCE — thread-safe by the class loader.

    1.6 Non-functional requirements

    • Correct under load — never two vehicles in one spot.
    • Fast enough — a linear scan over spots is fine for hundreds of spots. For thousands, keep a free-spot queue per type.
    • Extensible — new vehicle, pricing or payment needs no edit to ParkingLot.
    • Testable — times are passed in, so fees are predictable.
    Interview tipWrite the final requirements on the board, in these 4 buckets. Say “concurrency matters here” early. It is the part most candidates miss.

    2Core entities + breakdown

    Read the requirements again. Underline the nouns. Most nouns become classes. Verbs become methods.

    A parking lot has floors. Each floor has spots for one vehicle type. A vehicle enters at an entry gate and gets a ticket. At the exit gate the driver pays a fee by a payment mode. The fee comes from a pricing rule.

    “Fee” and “payment” are behaviour that varies, not data. So they become interfaces with many implementations: PricingStrategy and PaymentStrategy.

    EntityTypeResponsibility
    ParkingLotService / singletonHolds floors, active tickets and the pricing strategy. Parks and unparks vehicles.
    ParkingFloorModelHolds its spots by id. Finds and books a free spot of a type.
    ParkingSpotModelOne spot. Knows its allowed type. Books itself atomically (tryOccupy) and frees itself (vacate).
    Vehicle (abstract)ModelNumber plate and type.
    Car / Bike / TruckModelConcrete vehicles. Each one fixes its own VehicleType.
    TicketModelProof of entry: UUID, entry time, vehicle, floor id, spot id, payment status.
    Gate (abstract)ModelHas an id and a type.
    EntryGate / ExitGateModelEntry calls parkVehicle. Exit calls unparkVehicle.
    PricingStrategyInterfacecalculateFee(type, entry, exit). TimeBasedPricing, EventBasedPricing.
    PaymentStrategyInterfaceprocessPayment(ticket, amount). CashPayment, UpiPayment, CardPayment.
    PaymentProcessorServiceRuns one payment strategy. Sets the ticket’s payment status.
    VehicleFactory, PricingStrategyFactory, PaymentStrategyFactoryFactoryTurn an enum value into the right object.
    VehicleType, PaymentMode, PaymentStatus, PricingStrategyType, GateTypeEnumFixed sets of values.
    Common mistakeDo not write if (type == CAR) rate = 30 else if … and if (mode == UPI) … else if … inside ParkingLot. Every new rate or payment mode would edit the core class. Put each rule in its own strategy.
    Second common mistakeDo not make parkVehicle synchronized. It is correct, but every gate waits for every other gate. Lock (or CAS) only the one spot.

    5.3 ParkingSpot — the concurrency core

    model/ParkingSpot.java
    @Getter
@Setter
@RequiredArgsConstructor
public class ParkingSpot {
    private final String id;
    private final VehicleType allowedType;

    private AtomicBoolean occupied = new AtomicBoolean(false);

    public boolean tryOccupy() {
        return occupied.compareAndSet(false, true);   // only one thread wins
    }

    public void vacate() {
        occupied.set(false);
    }

    public boolean isOccupied() {
        return occupied.get();
    }
}

    Key idea. “Is it free?” and “take it” happen in one atomic step. With a plain boolean, two threads can both read false, then both write true. That is a check-then-act race. CAS removes it without a lock.

    5.4 ParkingFloor

    model/ParkingFloor.java
    @Getter
public class ParkingFloor {
    private final String id;
    private final Map<String, ParkingSpot> spots = new HashMap<>();

    public ParkingFloor(String id) { this.id = id; }

    public void addSpot(ParkingSpot spot) {
        spots.put(spot.getId(), spot);
    }

    public ParkingSpot findAvailableSpot(VehicleType vehicleType) {
        for (ParkingSpot spot : spots.values()) {
            if (spot.getAllowedType() == vehicleType && spot.tryOccupy()) {
                return spot;              // already booked for the caller
            }
        }
        return null;
    }
}

    The name says “find”, but the method also books the spot. That is on purpose: find and book must be one step. A better name is reserveSpot.

    5.6 Pricing strategies

    strategy/pricing/*.java · factory/PricingStrategyFactory.java
    public interface PricingStrategy {
    double calculateFee(VehicleType type, LocalDateTime entryTime, LocalDateTime exitTime);
}

public class TimeBasedPricing implements PricingStrategy {
    private static final LocalTime PEAK_START = LocalTime.of(8, 0);
    private static final LocalTime PEAK_END = LocalTime.of(17, 0);

    private boolean isPeak(LocalTime time) {
        return !time.isBefore(PEAK_START) && !time.isAfter(PEAK_END);   // ⚠ 17:00 slot counts as peak
    }

    @Override
    public double calculateFee(VehicleType type, LocalDateTime entryTime, LocalDateTime exitTime) {
        if (exitTime.isBefore(entryTime)) throw new IllegalArgumentException("Exit time before entry time");

        long durationMinutes = Duration.between(entryTime, exitTime).toMinutes();
        long totalHours = (long) Math.ceil(durationMinutes / 60.0);    // round up

        int peakHours = 0, nonPeakHours = 0;
        LocalDateTime cursor = entryTime.truncatedTo(ChronoUnit.HOURS);
        for (int i = 0; i < totalHours; i++) {                          // classify hour by hour
            if (isPeak(cursor.toLocalTime())) peakHours++; else nonPeakHours++;
            cursor = cursor.plusHours(1);
        }

        double peakRate    = switch (type) { case CAR -> 30.0; case BIKE -> 15.0; case TRUCK -> 50.0; };
        double nonPeakRate = switch (type) { case CAR -> 20.0; case BIKE -> 10.0; case TRUCK -> 30.0; };
        return peakHours * peakRate + nonPeakHours * nonPeakRate;
    }
}

public class EventBasedPricing implements PricingStrategy {
    private static final Map<VehicleType, Double> EVENT_HOURLY_RATES = Map.of(
            VehicleType.CAR, 50.0, VehicleType.BIKE, 30.0, VehicleType.TRUCK, 70.0);

    @Override
    public double calculateFee(VehicleType type, LocalDateTime entryTime, LocalDateTime exitTime) {
        long durationMinutes = Duration.between(entryTime, exitTime).toMinutes();
        long hours = (long) Math.ceil(durationMinutes / 60.0);
        return EVENT_HOURLY_RATES.getOrDefault(type, 0.0) * hours;
    }
}

public class PricingStrategyFactory {
    public static PricingStrategy get(PricingStrategyType type) {
        return switch (type) {
            case TIME_BASED -> new TimeBasedPricing();
            case EVENT_BASED -> new EventBasedPricing();
        };
    }
}

    Example: a car in at 7:30, out at 13:15 = 345 min → 6 hours. Slots start at 7, 8, 9, 10, 11, 12. One non-peak + five peak = 20 + 5 × 30 = ₹170. Event-based: 6 × 50 = ₹300.

    5.7 Payment strategies and PaymentProcessor

    strategy/payment/*.java · factory/PaymentStrategyFactory.java · service/PaymentProcessor.java
    public interface PaymentStrategy {
    boolean processPayment(Ticket ticket, double amount);
}

public class UpiPayment implements PaymentStrategy {
    @Override
    public boolean processPayment(Ticket ticket, double amount) {
        System.out.println("Paid ₹" + amount + " for ticket " + ticket.getTicketId() + " via UPI.");
        return true;
    }
}
// CashPayment and CardPayment look the same

public class PaymentStrategyFactory {
    public static PaymentStrategy get(PaymentMode mode) {
        return switch (mode) {
            case CASH -> new CashPayment();
            case UPI -> new UpiPayment();
            case CARD -> new CardPayment();
        };
    }
}

public class PaymentProcessor {
    private final PaymentStrategy strategy;

    public PaymentProcessor(PaymentStrategy strategy) { this.strategy = strategy; }

    public boolean pay(Ticket ticket, double amount) {
        boolean success = strategy.processPayment(ticket, amount);
        ticket.setPaymentStatus(success ? PaymentStatus.SUCCESS : PaymentStatus.FAILED);
        if (!success) System.out.println("Payment failed for ticket: " + ticket.getTicketId());
        return success;
    }
}

    PaymentProcessor is the Strategy context. It holds the shared steps (set status, log failure). Each strategy holds only the part that differs.

    5.9 ParkingLot — the orchestrator

    service/ParkingLot.java
    @Getter
public class ParkingLot {
    private static final ParkingLot INSTANCE = new ParkingLot();     // eager singleton

    private final Map<String, ParkingFloor> floors = new HashMap<>();
    private final Map<String, Ticket> activeTickets = new HashMap<>();  // ⚠ use ConcurrentHashMap
    @Setter
    private PricingStrategy pricingStrategy;

    private ParkingLot() {
        this.pricingStrategy = PricingStrategyFactory.get(PricingStrategyType.TIME_BASED);
    }

    public static ParkingLot getInstance() { return INSTANCE; }

    public void addFloor(ParkingFloor floor) { floors.put(floor.getId(), floor); }

    public Ticket parkVehicle(Vehicle vehicle, LocalDateTime entryTime) {
        for (ParkingFloor floor : floors.values()) {
            ParkingSpot spot = floor.findAvailableSpot(vehicle.getType());
            if (spot != null) {                                    // spot is already ours (CAS)
                String ticketId = UUID.randomUUID().toString();
                Ticket ticket = Ticket.builder()
                        .ticketId(ticketId).entryTime(entryTime).vehicle(vehicle)
                        .floorId(floor.getId()).spotId(spot.getId())
                        .build();
                activeTickets.put(ticketId, ticket);
                System.out.println("Vehicle parked. Ticket: " + ticketId);
                return ticket;
            }
        }
        System.out.println("No spot available for vehicle type: " + vehicle.getType());
        return null;
    }

    public void unparkVehicle(String ticketId, LocalDateTime exitTime, PaymentMode paymentMode) {
        Ticket ticket = activeTickets.get(ticketId);              // ⚠ two exits can both get it
        if (ticket == null) {
            System.out.println("Invalid ticket ID.");
            return;
        }

        double fee = pricingStrategy.calculateFee(ticket.getVehicle().getType(), ticket.getEntryTime(), exitTime);

        PaymentProcessor processor = new PaymentProcessor(PaymentStrategyFactory.get(paymentMode));
        if (!processor.pay(ticket, fee)) {
            System.out.println("Vehicle cannot exit. Payment unsuccessful.");
            return;
        }

        ParkingSpot spot = floors.get(ticket.getFloorId()).getSpots().get(ticket.getSpotId());
        spot.vacate();
        activeTickets.remove(ticketId);
        System.out.println("Vehicle exited. Fee charged: ₹" + fee);
    }

    public void printStatus() { /* prints each floor and each spot: Occupied / Free */ }
}

    Order matters. Park: book the spot, then write the ticket — no ticket ever points at a spot someone else holds. Unpark: take the money, then free the spot — a failed payment changes nothing.

    7Design patterns
    
  
    Be honest in the interview. Say which patterns the code uses and which ones you would add.
    
  
    
    
    Strategy used
    PricingStrategy (time / event) and PaymentStrategy (cash / UPI / card). PaymentProcessor is the context. Pricing can be swapped at runtime.
    
    
    Simple Factory used
    VehicleFactory, PricingStrategyFactory, PaymentStrategyFactory: enum in, object out. One switch per family, in one place.
    
    
    Singleton used
    ParkingLot.getInstance(), eager and thread-safe. Simple for one lot. The cost: shared state between tests, and no way to model two lots.
    
    
    Builder used
    Lombok @Builder on Ticket: named fields, no long constructor. Watch the @Builder.Default trap.
    
    
    Inheritance + polymorphism used
    Vehicle → Car / Bike / Truck. Gate → EntryGate / ExitGate.
    
    
    Lock-free CAS used
    Not GoF, but the key idea: AtomicBoolean.compareAndSet(false, true) books one spot without a lock.
    
    
    Strategy for spot choice would add
    SpotAllocationStrategy: first free, nearest to gate, lowest floor. Today the order is whatever HashMap gives.
    
    
    Observer would add
    Spots fire onOccupied / onFreed. A display board and a logger listen. Removes System.out from the model.
    
    
    Dependency injection would add
    Pass the ParkingLot into the gates instead of getInstance(). Tests get a fresh lot each time.
    
    
    One global lock avoid
    synchronized parkVehicle() works but makes all gates wait in line. Lock (or CAS) the spot, not the lot.
    
  
    
  
    SOLID check
    
      
      
    • S — Spot books itself, floor searches, pricing prices, payment pays. (System.out in the model breaks this a little.)
      • 
      
    • O — New pricing or payment: a new class + one factory case. ParkingLot does not change.
      • 
      
    • L — Any PricingStrategy works in the lot. But EventBasedPricing accepts exit < entry while TimeBasedPricing throws — the contract is not the same.
      • 
      
    • I — Each interface has one method.
      • 
      
    • D — ParkingLot depends on PricingStrategy (good) but calls static factories and gates call getInstance() (weak).
      • 
    
    
  
    
  
    Example: a spot-allocation strategy
    

    SpotAllocationStrategy.java
    public interface SpotAllocationStrategy {
    // returns a spot that is already booked (tryOccupy() == true), or null
    ParkingSpot allocate(Collection<ParkingFloor> floors, VehicleType type);
}

public class LowestFloorFirst implements SpotAllocationStrategy {
    public ParkingSpot allocate(Collection<ParkingFloor> floors, VehicleType type) {
        return floors.stream()
                .sorted(Comparator.comparing(ParkingFloor::getId))
                .map(f -> f.findAvailableSpot(type))
                .filter(Objects::nonNull)
                .findFirst().orElse(null);
    }
}

// In ParkingLot: ParkingSpot spot = allocationStrategy.allocate(floors.values(), vehicle.getType());
    
  
    The lot no longer decides which spot. A “nearest to gate” rule is one new class.
    

    

    



    

    
  
    8Similar problems
    
  
    A problem is similar only if the Parking Lot model carries over: a pool of typed slots, an atomic “book a free slot of this type” on entry, a ticket or session, and a fee + payment on release. The problems below share that skeleton. They are ranked by how much of this design you can reuse.

    Car rentalBranch → vehicles by type, VehicleFactory, pricing strategy (hourly / distance), payment strategy, booking as the ticket.Booking is for a time range, so “free” means no overlap with other bookings. Pick-up and drop at different branches.
    
      
    Hotel room bookingHotel → floors → rooms by type, book a free room of a type, check-in record, bill at check-out with a pricing strategy.Date-range availability. Reservations before arrival. Room states (clean, dirty, maintenance).
    
      
    Restaurant table bookingRestaurant → tables by size, book a free table that fits, release when the party leaves.Best-fit by party size. Time slots. Wait list when full.
    
      
    BookMyShow (seat booking)Theatre → screen → seats by type, like lot → floor → spot. Atomic seat lock under concurrency. Payment strategy.Shows and time. Many seats in one booking (all or none). Seat hold with a timeout before payment.
    
        
  
    

  
    Practice orderEV charging → Amazon locker → Restaurant table → Hotel → Car rental → BookMyShow. Each one adds one new idea to the same skeleton: size fit, time slots, date ranges, multi-seat locks.
