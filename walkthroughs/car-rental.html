Design a Car Rental System

Medium Java ~25 min read Code: org.nailyourinterview.lld.car_rental

A rental company has branches in many cities. Each branch has cars of a few types. A user picks a branch, a car type and a time window, pays, and gets a car. They may drop it at another branch.

The question tests three swappable rules — which car to give, how to price it, how to pay — and one hard case: two users book the last SUV at the same moment. The code answers the rules with three Strategy interfaces and the race with an AtomicBoolean and compareAndSet.

Every LLD answer follows the same 5 steps. Requirement gathering splits into 3 buckets: extensibility, dynamic input and high traffic. Click a step to jump to it.

    1.2 Core functional requirements

    • Branches (id, city) with vehicles grouped by type.
    • Vehicles with a plate, a type, a price per hour and per km, and a status.
    • Book: branch + type + start/end + distance + payment method + pickup/drop branch.
    • Pick one free car with a booking strategy; price it with a pricing strategy; pay with a payment strategy.
    • On payment failure, release the car. On success, store a CONFIRMED booking.
    • Return a car at the drop branch and complete the booking.
    • No double booking when many threads book at once.

    1.3 Extensibility (new features)

    Ask: “Which features may come next?” You do not build them now. You make sure each one is an addition, not a rewrite. For each feature, name the class that changes and the pattern that keeps the change small.

    1.4 Dynamic (user input)

    Nothing is hard-coded in the service. It comes in at runtime:

    • Branches and fleet: branchRepo.addBranch(...), branch.addVehicle(VehicleFactory.create(SUV, "NYB100", 30, 4)).
    • Dates as text: DateTimeParser.parse("21 May 7:30 AM 2025").
    • Rules: the booking and pricing strategy go into getInstance and can change with setters. The payment strategy comes with each call.
    Validate the inputThe code checks only that the branch exists and that a free car exists. It does not check start < end (a reversed window gives a negative price), distanceKm >= 0, or that branchId matches pickUpBranch — both are parameters and can disagree. DateTimeParser throws DateTimeParseException on bad text. Add these checks at the top of bookVehicle.

    1.5 High traffic (concurrency)

    Needed, and the code handles the core case. Main starts two threads that book the only SUV at once. Each vehicle has an AtomicBoolean isBooked. The booking strategy calls isBooked.compareAndSet(false, true): exactly one thread flips it and gets the car; the other gets false and tries the next car. No lock, no waiting.

    What is still missing for real traffic:

    • The repositories and Branch.vehicles are plain HashMap / ArrayList. Use ConcurrentHashMap and CopyOnWriteArrayList.
    • bookingCount++ is a plain int, read by other threads while they sort. Use AtomicInteger.
    • With many servers, an in-memory flag is not enough. Use a DB row lock, an optimistic version column, or a unique constraint on (vehicle, time slot).

    1.6 Non-functional requirements

    • No double booking — under any thread order.
    • Consistent rollback — a failed payment leaves no locked car behind.
    • Extensible — a new pricing, picking or payment rule is one new class.
    • Correct money — BigDecimal or cents in production; the code uses double.
    Interview tipSay “three strategies and one atomic flag” early. Then the interviewer knows you see both the extension points and the race.

@Setter
public abstract class Vehicle {
    private String licensePlate;
    private VehicleStatus status;
    private double pricePerHour;
    private double pricePerKm;
    private VehicleType type;
    private int bookingCount = 0;

    private final AtomicBoolean isBooked = new AtomicBoolean(false);   // the lock

    public Vehicle(String licensePlate, double pricePerHour, double pricePerKm, VehicleType type) {
        this.licensePlate = licensePlate;
        this.status = VehicleStatus.AVAILABLE;
        this.pricePerHour = pricePerHour;
        this.pricePerKm = pricePerKm;
        this.type = type;
    }

    public void incrementBookingCount() { this.bookingCount++; }
}

public class Sedan extends Vehicle {
    public Sedan(String licensePlate, double pricePerHour, double pricePerKm) {
        super(licensePlate, pricePerHour, pricePerKm, VehicleType.SEDAN);
    }
}
public class SUV extends Vehicle { /* same, VehicleType.SUV */ }

public class VehicleFactory {
    public static Vehicle create(VehicleType type, String licensePlate, double pricePerHour, double pricePerKm) {
        return switch (type) {
            case SEDAN -> new Sedan(licensePlate, pricePerHour, pricePerKm);
            case SUV -> new SUV(licensePlate, pricePerHour, pricePerKm);
        };
    }
}

    Two flags. status is the business state (AVAILABLE, BOOKED, IN_SERVICE…). isBooked is the thread-safe lock used during booking. The switch expression has no default: a new enum value is a compile error until you add its case — a good thing.

    5.5 BookingStrategy — pick and lock a car

    strategy/booking/*.java
    public interface BookingStrategy {
    Vehicle bookVehicle(List<Vehicle> vehicles);
}

public class LeastBookedVehicleStrategy implements BookingStrategy {
    @Override
    public Vehicle bookVehicle(List<Vehicle> vehicles) {
        List<Vehicle> sortedVehicles = vehicles.stream()
                .sorted(Comparator.comparingInt(Vehicle::getBookingCount))
                .toList();
        for (Vehicle vehicle : sortedVehicles) {
            // Attempt to atomically set isBooked from false to true
            if (vehicle.getIsBooked().compareAndSet(false, true)) {
                return vehicle;               // successfully booked
            }
            // else, this vehicle is already booked, try next
        }
        return null;                          // no vehicle could be booked
    }
}

@AllArgsConstructor
public class CheapestBookingStrategy implements BookingStrategy {
    private final PricingStrategyType pricingType;

    @Override
    public Vehicle bookVehicle(List<Vehicle> vehicles) {
        List<Vehicle> sortedVehicles = vehicles.stream()
                .sorted((v1, v2) -> {
                    double val1 = pricingType == PricingStrategyType.TIME_BASED ? v1.getPricePerHour() : v1.getPricePerKm();
                    double val2 = pricingType == PricingStrategyType.TIME_BASED ? v2.getPricePerHour() : v2.getPricePerKm();
                    return Double.compare(val1, val2);
                })
                .toList();
        for (Vehicle vehicle : sortedVehicles) {
            if (vehicle.getIsBooked().compareAndSet(false, true)) return vehicle;
        }
        return null;
    }
}

    The heart of the design. Sorting is the policy; compareAndSet(false, true) is the lock. CAS reads and writes in one atomic step, so only one thread sees true. The loser does not wait — it moves to the next car in the sorted list. Both strategies repeat the CAS loop; a small base class or a helper would remove the copy.

    5.6 PricingStrategy

    strategy/pricing/*.java
    public interface PricingStrategy {
    double calculatePrice(Vehicle vehicle, LocalDateTime start, LocalDateTime end, double distanceKm);
}

public class HourlyPricingStrategy implements PricingStrategy {
    @Override
    public double calculatePrice(Vehicle vehicle, LocalDateTime start, LocalDateTime end, double distanceKm) {
        long minutes = Duration.between(start, end).toMinutes();
        long hours = (long) Math.ceil(minutes / 60.0);          // 5 h 15 min → 6 h
        return vehicle.getPricePerHour() * hours;
    }
}

public class DistanceBasedPricingStrategy implements PricingStrategy {
    @Override
    public double calculatePrice(Vehicle vehicle, LocalDateTime start, LocalDateTime end, double distanceKm) {
        return distanceKm * vehicle.getPricePerKm();
    }
}

    One wide signature serves both rules: hourly ignores distanceKm, distance ignores the times. Main: SUV at $30/h from 7:30 to 12:30 → 300 min → 5 h → $150.00.

    5.7 PaymentStrategy and PaymentProcessor

    strategy/payment/*.java · service/PaymentProcessor.java
    public interface PaymentStrategy {
    boolean processPayment(Booking booking);
}

public class CreditCardPaymentStrategy implements PaymentStrategy {
    @Override
    public boolean processPayment(Booking booking) {
        // Simulate credit card processing
        System.out.println("Processing credit card payment for booking: " + booking.getBookingId());
        return true;
    }
}
// WalletPaymentStrategy: same, prints "Processing wallet payment ..."

public class PaymentProcessor {
    private final PaymentStrategy paymentStrategy;

    public PaymentProcessor(PaymentStrategy paymentStrategy) { this.paymentStrategy = paymentStrategy; }

    public boolean pay(Booking booking) {
        boolean success = paymentStrategy.processPayment(booking);
        if (success) {
            booking.setPaymentStatus(PaymentStatus.SUCCESS);
        } else {
            booking.setPaymentStatus(PaymentStatus.FAILED);
            System.out.println("Payment Failed!");
        }
        return success;
    }
}

    The strategies only talk to the “bank”. PaymentProcessor owns the shared step — writing the payment status — so each new method does not repeat it.

    5.8 BookingService — the orchestrator

    service/BookingService.java
    public class BookingService {
    private static volatile BookingService instance;

    private final BranchRepository branchRepo;
    private final BookingRepository bookingRepo;
    @Setter private BookingStrategy bookingStrategy;
    @Setter private PricingStrategy pricingStrategy;

    private BookingService(BranchRepository branchRepo, BookingRepository bookingRepo,
                           BookingStrategy bookingStrategy, PricingStrategy pricingStrategy) { /* assign all four */ }

    public static BookingService getInstance(BranchRepository branchRepo, BookingRepository bookingRepo,
                                             BookingStrategy bookingStrategy, PricingStrategy pricingStrategy) {
        if (instance == null) {
            synchronized (BookingService.class) {
                if (instance == null) {
                    instance = new BookingService(branchRepo, bookingRepo, bookingStrategy, pricingStrategy);
                }
            }
        }
        return instance;
    }

    public Optional<Booking> bookVehicle(String branchId, VehicleType vehicleType,
                                         LocalDateTime start, LocalDateTime end, User user,
                                         PaymentStrategy paymentStrategy,
                                         Branch pickUpBranch, Branch dropBranch, double distanceKm) {
        Branch branch = branchRepo.getBranch(branchId);
        if (branch == null) { System.out.println("Branch not found"); return Optional.empty(); }

        List<Vehicle> activeVehicles = branch.getVehiclesByType(vehicleType).stream()
                .filter(v -> v.getStatus() == VehicleStatus.AVAILABLE)
                .filter(v -> !v.getIsBooked().get())
                .toList();
        if (activeVehicles.isEmpty()) {
            System.out.println("No active " + vehicleType.name() + " vehicles available.");
            return Optional.empty();
        }

        // Booking strategy tries to createBooking and return a vehicle with atomic isBooked set
        Vehicle vehicle = bookingStrategy.bookVehicle(activeVehicles);
        if (vehicle == null) { System.out.println("No vehicle could be booked."); return Optional.empty(); }

        double amount = pricingStrategy.calculatePrice(vehicle, start, end, distanceKm);

        Booking booking = Booking.builder()
                .bookingId(UUID.randomUUID().toString())
                .user(user).vehicle(vehicle)
                .pickupBranch(pickUpBranch).dropBranch(dropBranch)
                .startTime(start).endTime(end)
                .amount(amount)
                .build();

        PaymentProcessor processor = new PaymentProcessor(paymentStrategy);
        if (!processor.pay(booking)) {
            System.out.println("Payment failed");
            vehicle.getIsBooked().set(false);          // Rollback booking if payment fails
            return Optional.empty();
        }

        booking.setStatus(BookingStatus.CONFIRMED);
        bookingRepo.addBooking(booking);
        vehicle.incrementBookingCount();
        vehicle.setStatus(VehicleStatus.BOOKED);
        System.out.println(booking);
        return Optional.of(booking);
    }

    public void returnVehicle(String bookingId) {
        Booking booking = bookingRepo.getBookingById(bookingId)
                .orElseThrow(() -> new RuntimeException("Booking not found"));   // repo: isEmpty() + throw
        if (booking.getStatus() != BookingStatus.CONFIRMED) {
            throw new RuntimeException("Vehicle is not currently booked");
        }
        booking.setStatus(BookingStatus.COMPLETED);
        booking.getVehicle().getIsBooked().set(false);

        Branch dropBranch = booking.getDropBranch();
        dropBranch.addVehicle(booking.getVehicle());
        System.out.println("Vehicle returned to branch " + dropBranch.getCity() + ": " + booking.getVehicle().getLicensePlate());
    }
}

    Order matters. Lock the car (CAS) → price → pay → confirm. If payment fails, the lock is released. Read returnVehicle closely — it frees isBooked but leaves status == BOOKED, so the filter above never offers the car again. It also adds the car to the drop branch without removing it from the pickup branch. Both bugs are in “Traps → fixes”.

    7Design patterns
    
  
    Be honest in the interview. Say which patterns the code uses and which ones you would add.
    
  
    
    
    Strategy × 3 used
    BookingStrategy (which car), PricingStrategy (how much), PaymentStrategy (how to pay). Two implementations each.
    
    
    Factory used
    VehicleFactory.create(type, …) hides new Sedan / new SUV from the client.
    
    
    Builder used
    Lombok @Builder on Booking: 10 fields, readable construction.
    
    
    Repository used
    BranchRepository, BookingRepository: storage behind a small API; swap for a DB later.
    
    
    Optimistic lock (CAS) used
    AtomicBoolean.compareAndSet per car: lock-free, losers move on to the next car.
    
    
    State would add
    Booking lifecycle (CREATED → CONFIRMED → COMPLETED / CANCELLED) with rules per state: cancel fees, late-return fees.
    
    
    Decorator / Observer would add
    Decorator for add-ons on the price (insurance, GPS). Observer for confirm / return notifications.
    
    
    Singleton with arguments avoid
    getInstance(repos, strategies) silently ignores its arguments after the first call. Hard to test. Create the service once and pass it in.
    
  
    
  
    SOLID check
    
      
      
    • S — Mostly. BookingService.bookVehicle filters, locks, prices, builds, pays and stores; an AvailabilityService could take the first part.
      • 
      
    • O — New pricing, picking or payment = new class. A new vehicle type edits VehicleFactory (one case).
      • 
      
    • L — Any strategy works in place of another. CheapestBookingStrategy keeps its own PricingStrategyType, so it can rank by hour while the bill is per km.
      • 
      
    • I — Small interfaces, one method each. calculatePrice takes both time and km so each rule can ignore one.
      • 
      
    • D — The service depends on the three interfaces, injected.
      • 
    
    
  
    
  
    Example: real availability by date (wire in the unused checker)
    

    Vehicle.java (would add)
    // Each car keeps its own bookings. A car is free if no active booking overlaps the window.
private final List<Booking> bookings = new ArrayList<>();

public synchronized boolean tryReserve(Booking booking) {
    if (!VehicleAvailabilityChecker.isAvailable(bookings, booking.getStartTime(), booking.getEndTime())) {
        return false;
    }
    bookings.add(booking);
    return true;
}

// In the strategy, replace isBooked.compareAndSet(false, true) with:
//     if (vehicle.tryReserve(booking)) return vehicle;
// On payment failure, remove the booking instead of isBooked.set(false).
    
  
    Now a car booked for 21 May is still free on 25 May. A per-car synchronized replaces the CAS, because “check overlap, then add” is two steps. Also fix the checker: it treats back-to-back rentals (one ends at 12:30, the next starts at 12:30) as an overlap. Use end.isAfter(existingStart) && start.isBefore(existingEnd).
    

    

    



    

    
  
    8Similar problems
    
  
    A problem is similar only if the rental model carries over: locations hold a stock of units grouped by type; a user asks for a type and a time window; a rule picks one free unit and locks it; a rule prices it; the user pays; later the unit comes back. The problems below share that skeleton. They are ranked by how much of this design you can reuse.
    

  
    The shared skeleton
    
    Location → units by type · filter free → strategy picks + locks (CAS) → price → pay (rollback on fail) → confirm · return frees the unit.

    Bike / scooter rental
    closest    		Almost all: stations = branches, bike types, per-minute pricing, CAS lock, drop at another station.Unlock by QR, live battery level, price known only at return.
    
      
    Hotel room bookingHotel = branch, room type = vehicle type, pick strategy, pricing strategy, payment + rollback.Date ranges are the core (the fix in §7), nightly rates, cancellation policy.
    
      
    Equipment / tool rentalStores, item types, hourly or daily price, deposit on return.Quantity per item, damage check on return.
    
      
    Meeting room / desk bookingFloors = branches, room types, “pick one free” strategy, lock against double booking.Time slots in a calendar, recurring bookings, usually free (no payment).
    
      
    Doctor’s appointmentDoctors by specialization like cars by type; book a slot; one patient per slot.The unit is a time slot, not an object. This repo has it: lld/doctors_appointment.
