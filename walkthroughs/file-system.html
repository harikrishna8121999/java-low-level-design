Design an In-Memory File System

Medium Java ~25 min read Code: org.nailyourinterview.lld.file_system

Build a small Unix-like file system in memory. Users make directories, write and read files, move and delete them, and search the tree. Paths can be absolute (/home/bob) or relative to a working directory (../bob).

The question tests three decisions. How do you model files and folders? As one tree: a Directory holds Entry objects, and both File and Directory are entries — the Composite pattern. How do you turn a path into a node? One resolve() walk from the root or from the working directory. How do you search with many rules? Small filter objects that you combine with and().

Every LLD answer follows the same 5 steps. Requirement gathering splits into 3 buckets: extensibility, dynamic input and high traffic. Click a step to jump to it.

    1.2 Core functional requirements

    • One tree with a root /. A directory holds files and directories. Names are unique inside one directory.
    • mkdir creates every missing directory on the path.
    • Create a file; write (overwrite, create if missing); append; read.
    • ls lists the children of a directory, sorted by name, with sizes.
    • cd / pwd: a working directory for relative paths.
    • mv moves into an existing directory, or renames to a new path.
    • rm deletes a file, or a directory with everything under it.
    • Size: a file's size is its content length; a directory's size is the sum of its children.
    • Search under a path with one or more filters.
    • Reject bad input: missing path, name clash, file used as a directory (or the reverse), moving a directory into itself, deleting the root or the working directory.

    1.4 Dynamic (user input)

    Nothing is hard-coded. Every path and every piece of text comes in at runtime:

    • Paths: mkdir("/home/alice/docs"), cd("../bob"), move("/home/bob/resume.txt", "/home/bob/cv.txt").
    • Content: writeFile(path, text), appendFile(path, text).
    • Search rules: search("/home", new NameContainsFilter("o").and(new ExtensionFilter("md"))).
    Validate the inputA path part can be missing. A file can sit where a directory is needed (mkdir /home/bob/todo.txt/x, cd /tmp/cache.log), or the reverse (cat /home). A name can clash. A move can target the source's own subtree. A delete can target the root or the working directory. Each check prints one clear message and returns early. Nothing changes on failure.

    1.5 High traffic (concurrency)

    Not needed for the interview answer — one user, one shell. The code is single-threaded: plain TreeMap children and one current field. Say so, then say what a shared file system needs:

    • Working directory per user. current moves into a Session object. Two users must not share one cd.
    • Simple lock. One ReentrantReadWriteLock for the tree. ls, cat, search take the read lock; mkdir, write, mv, rm take the write lock. Easy and correct; writers wait.
    • Finer locks. One lock per directory. Lock from the root down (parent before child). mv locks both parents in path order, so two moves cannot deadlock.
    • At real scale (HDFS, GFS): a metadata server holds the tree; data servers hold file blocks. Clients ask the metadata server for block locations, then read data directly.

    1.6 Non-functional requirements

    • Correct — the tree never gets a cycle; no orphan working directory.
    • Fast lookup — each path part is one map lookup: O(depth).
    • Readable — ls output is sorted (a TreeMap).
    • Extensible — a new search rule or a new entry type is one new class.
    Interview tipSay early: “A file and a directory are both entries. A directory holds entries.” Draw that triangle first. Size, search, move and delete all follow from it.

    2Core entities + breakdown

    Read the requirements again. Underline the nouns. Most nouns become classes. Verbs become methods.

    The file system is a tree with a root. A directory holds files and other directories. Each has a name and a parent. A user makes directories, writes and reads files, moves and deletes them, using a path from the root or from the working directory. A user also searches with one or more filters.

    “File” and “directory” share name, parent, path and size, so they get a common parent class: Entry. “Root” and “working directory” are not classes — they are two Directory fields in FileSystem. “Path” is a String; resolve() turns it into an Entry. “Filter” changes often, so it is an interface.

    EntityTypeResponsibility
    FileSystemServiceThe one entry point. Holds root and current. Resolves paths, validates input, runs every command.
    EntryAbstract className and parent. getPath() walks up to the root. getSize() and isDirectory() are abstract.
    FileLeafContent in a StringBuilder. Read, write, append, extension. Size = content length.
    DirectoryCompositechildren: TreeMap<name, Entry>. Add, remove, get a child. Size = sum of children.
    SearchFilterInterfacematches(entry), plus a default and(other) to combine filters.
    ExtensionFilter / MinSizeFilter / NameContainsFilterStrategyFiles with extension X / files of at least N bytes / entries whose name contains S.
    Common mistakeA Directory with two maps: files and subDirs. Then a file and a folder can have the same name, every method checks two maps, and size, search, move and delete each need two code paths. One map of Entry fixes all of it.

    4Move flow

    Most commands are “resolve, check the type, change one map”. move has the most checks, so it is the one to draw. It decides between “move into a directory” and “rename”, then stops a directory from moving into its own subtree.

    FileSystem.move() flowchart
    Example: mv /home /home/alice. The target is a directory, so the new parent is /home/alice. Walk up from it: alice → home. We meet the source, so refuse. Without the check, /home would become its own grandchild and drop out of the tree.

    5Working code

    Build bottom-up: Entry, then File and Directory, then the filters, then FileSystem. The code uses Lombok (@Getter, @Setter, @AllArgsConstructor) to remove boilerplate.

    5.1 Entry — the shared base

    model/Entry.java
    // One node in the tree. A file and a directory are both entries (Composite).
@Getter
public abstract class Entry {
    @Setter private String name;
    @Setter private Directory parent;   // null only for the root

    protected Entry(String name) {
        this.name = name;
    }

    public abstract int getSize();

    public abstract boolean isDirectory();

    // Walk up to the root: /docs/notes.txt
    public String getPath() {
        if (parent == null) return "/";
        String parentPath = parent.getPath();
        return (parentPath.equals("/") ? "" : parentPath) + "/" + name;
    }
}

    Why compute the path, not store it? A stored path goes stale on every mv of any ancestor. Moving /home would mean rewriting every path under it. With a parent link, a move is one map change and every path below is right at once.

    5.2 File and Directory — leaf and composite

    model/File.java · model/Directory.java
    public class File extends Entry {
    private final StringBuilder content = new StringBuilder();

    public File(String name) {
        super(name);
    }

    public String read() {
        return content.toString();
    }

    public void write(String text) {
        content.setLength(0);
        content.append(text);
    }

    public void append(String text) {
        content.append(text);
    }

    public String getExtension() {
        int dot = getName().lastIndexOf('.');
        return dot < 0 ? "" : getName().substring(dot + 1);
    }

    @Override
    public int getSize() {
        return content.length();
    }

    @Override
    public boolean isDirectory() {
        return false;
    }
}

public class Directory extends Entry {
    private final Map<String, Entry> children = new TreeMap<>();   // name -> entry, sorted for ls

    public Directory(String name) {
        super(name);
    }

    public Entry getChild(String name) { return children.get(name); }
    public boolean hasChild(String name) { return children.containsKey(name); }
    public Collection<Entry> getChildren() { return children.values(); }

    public void addChild(Entry entry) {
        children.put(entry.getName(), entry);
        entry.setParent(this);
    }

    public void removeChild(String name) {
        Entry entry = children.remove(name);
        if (entry != null) entry.setParent(null);
    }

    // Composite: a directory's size is the sum of its children
    @Override
    public int getSize() {
        return children.values().stream().mapToInt(Entry::getSize).sum();
    }

    @Override
    public boolean isDirectory() {
        return true;
    }
}

    The Composite in one line: Directory.getSize() calls getSize() on each child and does not care if the child is a file or a folder. The recursion ends at the files. Why a TreeMap? O(log n) lookup by name, and ls comes out sorted for free. Why no getter for the map? getChildren() returns values only; all changes go through addChild / removeChild, which keep the parent link right.

    5.3 SearchFilter — what to find

    search/SearchFilter.java · ExtensionFilter.java · MinSizeFilter.java · NameContainsFilter.java
    public interface SearchFilter {
    boolean matches(Entry entry);

    default SearchFilter and(SearchFilter other) {
        return entry -> matches(entry) && other.matches(entry);
    }
}

@AllArgsConstructor
public class ExtensionFilter implements SearchFilter {
    private final String extension;

    @Override
    public boolean matches(Entry entry) {
        return entry instanceof File file && file.getExtension().equals(extension);
    }
}

@AllArgsConstructor
public class MinSizeFilter implements SearchFilter {
    private final int minSize;

    @Override
    public boolean matches(Entry entry) {
        return !entry.isDirectory() && entry.getSize() >= minSize;
    }
}

@AllArgsConstructor
public class NameContainsFilter implements SearchFilter {
    private final String text;

    @Override
    public boolean matches(Entry entry) {
        return entry.getName().contains(text);
    }
}

    Why a default and()? “.md files with an o in the name” needs no new class: new NameContainsFilter("o").and(new ExtensionFilter("md")). or() and not() are two more default methods. The search walk never changes.

    5.4 FileSystem — paths and commands

    service/FileSystem.java (core methods)
    public class FileSystem {
    private final Directory root = new Directory("");
    private Directory current = root;   // working directory for relative paths

    // Absolute (/a/b) or relative to the working directory (a/b, ../b, ./b).
    // Returns null if any part is missing.
    private Entry resolve(String path) {
        Entry entry = path.startsWith("/") ? root : current;
        for (String part : path.split("/")) {
            if (part.isEmpty() || part.equals(".")) continue;
            if (part.equals("..")) {
                entry = entry.getParent() == null ? entry : entry.getParent();
                continue;
            }
            if (!(entry instanceof Directory dir)) return null;
            entry = dir.getChild(part);
            if (entry == null) return null;
        }
        return entry;
    }

    // Like mkdir -p: create every missing directory on the path
    public boolean mkdir(String path) {
        Directory dir = path.startsWith("/") ? root : current;
        for (String part : path.split("/")) {
            if (part.isEmpty() || part.equals(".")) continue;
            if (part.equals("..")) { dir = dir.getParent() == null ? dir : dir.getParent(); continue; }
            Entry child = dir.getChild(part);
            if (child == null) {
                child = new Directory(part);
                dir.addChild(child);
            } else if (!child.isDirectory()) {
                System.out.println("mkdir: " + child.getPath() + " is a file.");
                return false;
            }
            dir = (Directory) child;
        }
        System.out.println("mkdir " + dir.getPath());
        return true;
    }

    // Overwrite. Create the file first if it is missing.
    public boolean writeFile(String path, String text) {
        Entry entry = resolve(path);
        if (entry == null) {
            if (!createFile(path)) return false;
            entry = resolve(path);
        }
        File file = asFile(entry, "write");
        if (file == null) return false;
        file.write(text);
        return true;
    }

    // Delete a file, or a directory with everything under it (rm -r)
    public boolean delete(String path) {
        Entry entry = find(path, "rm");
        if (entry == null) return false;
        if (entry == root) { System.out.println("rm: cannot delete the root."); return false; }
        if (isSameOrInside(current, entry)) {
            System.out.println("rm: " + entry.getPath() + " holds the working directory.");
            return false;
        }
        entry.getParent().removeChild(entry.getName());
        return true;
    }

    // mv: into an existing directory, or to a new path (rename)
    public boolean move(String from, String to) {
        Entry source = find(from, "mv");
        if (source == null) return false;
        if (source == root) { System.out.println("mv: cannot move the root."); return false; }

        Entry target = resolve(to);
        Directory newParent;
        String newName;
        if (target != null && target.isDirectory()) {
            newParent = (Directory) target;
            newName = source.getName();
        } else {
            newParent = findDirectory(parentOf(to), "mv");
            newName = nameOf(to);
            if (newParent == null || !isValidName(newName)) return false;
        }

        if (isSameOrInside(newParent, source)) {
            System.out.println("mv: cannot move " + source.getPath() + " inside itself.");
            return false;
        }
        if (newParent.hasChild(newName)) {
            System.out.println("mv: " + newParent.getChild(newName).getPath() + " already exists.");
            return false;
        }

        source.getParent().removeChild(source.getName());
        source.setName(newName);
        newParent.addChild(source);
        return true;
    }

    public List<String> search(String path, SearchFilter filter) {
        List<String> found = new ArrayList<>();
        Entry start = find(path, "find");
        if (start != null) collect(start, filter, found);
        return found;
    }

    // Depth-first walk of the tree
    private void collect(Entry entry, SearchFilter filter, List<String> found) {
        if (filter.matches(entry)) found.add(entry.getPath());
        if (entry instanceof Directory dir) {
            dir.getChildren().forEach(child -> collect(child, filter, found));
        }
    }

    // Walk up from 'entry'. True if we meet 'ancestor' on the way.
    private boolean isSameOrInside(Entry entry, Entry ancestor) {
        for (Entry e = entry; e != null; e = e.getParent()) {
            if (e == ancestor) return true;
        }
        return false;
    }

    // cd, pwd, ls, createFile, appendFile, readFile, tree,
    // find / findDirectory / asFile print the error and return null,
    // parentOf / nameOf split a path, isValidName rejects "", "." and ".."
}

    One resolve() for every command. Absolute vs relative is one line: the start node. .. at the root stays at the root, like Unix. One helper for two guards. isSameOrInside stops mv /home /home/alice (a cycle) and rm /home while you stand in /home/bob (a dangling working directory). Why remove before rename? The map key is the name. Remove with the old name, then rename, then add with the new name.

    7Design patterns
    
  
    Be honest in the interview. Say which patterns the code uses and which ones you would add.
    
  
    
    
    Composite used
    Entry ← File (leaf), Directory (composite, holds entries). getSize(), getPath() and the search walk treat both the same.
    
    
    Strategy / Specification used
    SearchFilter with three rules and a default and() to combine them. A new rule is a new class or a lambda.
    
    
    Facade / service used
    FileSystem is the one entry point. Callers pass path strings; they never touch a Directory map.
    
    
    Visitor would add
    Size, search, tree print and export are all walks. An EntryVisitor with visitFile / visitDirectory removes the instanceof checks and adds walks without editing the nodes.
    
    
    Command would add
    MkdirCommand, MoveCommand, … with execute() / undo(). Gives undo, a history and a queue for one writer thread.
    
    
    Observer would add
    FileWatcher listeners get “created / changed / deleted” events, like inotify or an IDE that reloads a file.
    
    
    Proxy would add
    A permission-checking FileSystem wrapper, or a lazy File that loads content from disk on first read.
    
    
    Two maps per directory avoid
    files + subDirs doubles every method and lets a file and a folder share a name. Also avoid a Singleton FileSystem: tests need fresh trees.
    
  
    
  
    SOLID check
    
      
      
    • S — Entry: name, parent, path. Directory: children. File: content. FileSystem: paths and commands. Filters: one rule each.
      • 
      
    • O — A new search rule is a new class. A new entry type (link) edits resolve() — the known weak spot, which a Visitor would ease.
      • 
      
    • L — Any Entry works in getSize(), getPath() and the search walk.
      • 
      
    • I — SearchFilter has one abstract method.
      • 
      
    • D — search() depends on SearchFilter, not on a concrete rule. But FileSystem creates File and Directory with new — an EntryFactory would help once links arrive.
      • 
    
    
  
    
  
    Example: new search rules, no change to the walk
    

    search/GlobFilter.java (would add)
    public class GlobFilter implements SearchFilter {
    private final Pattern pattern;

    public GlobFilter(String glob) {                 // "*.md", "note?.txt"
        this.pattern = Pattern.compile(glob.replace(".", "\\.")
                .replace("*", ".*").replace("?", "."));
    }

    @Override
    public boolean matches(Entry entry) {
        return pattern.matcher(entry.getName()).matches();
    }
}

fs.search("/", new GlobFilter("*.md").and(new MinSizeFilter(10)));

// SearchFilter has one abstract method, so a lambda works too: empty folders
fs.search("/", e -> e.isDirectory() && e.getSize() == 0);
    
  
    No line in FileSystem changes. That is the Open/Closed principle at work.
    

    

    



    

    
  
    8Similar problems
    
  
    A problem is similar only if the tree model carries over: nodes that are either leaves or containers, a parent link, lookup by path, a value that rolls up from the leaves, and moves that must not make a cycle. The problems below share that skeleton. They are ranked by how much of this design you can reuse.

    // Composite: a folder's size is the sum of its children
int getSize() { return children.values().stream().mapToInt(Entry::getSize).sum(); }

// One walk for every path
Entry e = path.startsWith("/") ? root : current;
for (String part : path.split("/")) {
    if (part.isEmpty() || part.equals(".")) continue;
    if (part.equals("..")) { e = e.getParent() == null ? e : e.getParent(); continue; }
    if (!(e instanceof Directory d) || (e = d.getChild(part)) == null) return null;
}

// mv / rm guard: walk up, meet the source → refuse
for (Entry x = newParent; x != null; x = x.getParent()) if (x == source) return false;
    
      
    
    
    
  
    

  
    Traps → fixes
    
  
    
    
      
    Two maps per directory (files, subDirs) → name clash, double codeOne Map<name, Entry> (done)
    
      
    Store the full path in each node → stale after every mv of an ancestorStore the parent; compute the path (done)
    
      
    mv /home /home/alice → a cycle; the subtree drops out of the treeWalk up from the new parent; meet the source → refuse (done)
    
      
    rm the folder you stand in → cd .. from a detached nodeSame walk from current (done)
    
      
    mkdir /a/b/file.txt/c creates a and b, then fails → half doneCheck the whole path first, then create; or roll back the new nodes
    
      
    Directory.getSize() walks the whole subtree on every call → slow on big treesCache the size in each directory; on write, add the change to every ancestor (O(depth))
    
      
    rm on a folder deletes everything with no flagAdd recursive; refuse a non-empty folder without it
    
      
    Recursive walk on a very deep tree → StackOverflowErrorUse an explicit Deque stack for collect and printTree
    
      
    One current field → all users share one cd; plain TreeMap is not thread-safeSession per user; a read-write lock, or per-directory locks taken top-down
