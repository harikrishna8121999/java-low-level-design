Design an Elevator System

Medium Java ~25 min read Code: org.nailyourinterview.lld.elevator

A building has floors and a few elevators. People press ▲ or ▼ on a floor, and riders press a floor button inside a car. The system picks a car for each call and moves every car in a sensible order.

The question tests two decisions. Which car answers a hall call? That is a swappable Strategy. In which order does a car serve its stops? That is the LOOK rule: keep the direction while stops lie ahead, then turn. A sorted set of floors makes LOOK a few lines.

Every LLD answer follows the same 5 steps. Requirement gathering splits into 3 buckets: extensibility, dynamic input and high traffic. Click a step to jump to it.

LLD interview flow — applied to Elevator System

    1.2 Core functional requirements

    • A building with floors 0 … N-1 and M elevators. All start at floor 0.
    • Hall call (floor + direction): the controller picks one car with a scheduling strategy.
    • Car call: a rider picks a floor inside a car.
    • Each tick, every car moves one floor. It serves stops in LOOK order and opens its doors at each stop.
    • Status of each car: floor, direction, pending stops, doors.
    • Maintenance: take a car out only when it has no stops. The strategy skips it; car calls are rejected.
    • Reject bad input: unknown floor, ▲ on the top floor, ▼ on floor 0, unknown car.

    1.3 Extensibility (new features)

    1.4 Dynamic (user input)

    Nothing is hard-coded in the classes. It comes in at runtime:

    • Building size and the rule: new ElevatorController(10, 2, new NearestElevatorStrategy()).
    • Hall calls: requestElevator(4, Direction.UP) — at any time, also while cars move.
    • Car calls: selectFloor("E1", 7).
    • Operator: setMaintenance("E2", true).
    Validate the inputThe controller rejects a floor outside 0 … top, ▲ on the top floor, ▼ on floor 0, Direction.IDLE as a button, an unknown car id and a car call to a car that is out of service. The same floor pressed twice is stored once, because stops is a set.

    1.5 High traffic (concurrency)

    Needed in a real building, not in this code. Many people press buttons at once, and a timer moves the cars. The code here is a single-thread simulation: every call and every step() runs one after another. Say this out loud.

    For a real system, pick one of two designs:

    • One controller thread. Buttons put requests on a BlockingQueue. One thread takes them, picks a car and calls addStop. A scheduler calls step(). No locks in the model.
    • Locks. select() + addStop() must be one atomic action, or two calls read the same old state and both pick the same car. Use a lock in the controller and make Elevator.addStop / step synchronized (or keep stops in a ConcurrentSkipListSet).

    1.6 Non-functional requirements

    • No starvation — LOOK serves every stop within one sweep up and one sweep down.
    • Short waits — the strategy sends the car that arrives first.
    • Safe — a car out of service never moves or gets calls.
    • Extensible — a new dispatch rule is one new class.
    Interview tipSeparate the two questions early: “which car” lives in the controller + strategy; “which order” lives in the elevator. Most weak answers mix them in one big method.

    2Core entities + breakdown

    Read the requirements again. Underline the nouns. Most nouns become classes. Verbs become methods.

    A building has floors and elevators. A person on a floor presses a hall call (▲ or ▼). The controller picks a car with a scheduling rule. A rider inside presses a floor button. Each elevator keeps its stops, its direction and its doors, and moves one floor per tick.

    “Building” and “controller” are the same object here: the controller owns the floor range and the cars. “Floor” needs no class — it is an int. “Floor button” is a call to selectFloor. “Scheduling rule” is an interface, because it will change.

    EntityTypeResponsibility
    ElevatorControllerServiceHolds the cars, the top floor and the strategy. Validates input. Hall call → strategy → addStop. Car call → addStop. Drives time with step().
    ElevatorModelFloor, direction, doors, in-service flag and a sorted set of stops. step() moves one floor in LOOK order.
    RequestValue objectA hall call: floor + direction. The input to the strategy.
    SchedulingStrategyInterfaceselect(elevators, request) → a car, or null.
    NearestElevatorStrategyStrategyLowest travel cost. Idle or on the way: the distance. Going away: to its last stop, then back.
    DirectionEnumUP, DOWN, IDLE.
    Common mistakeA FIFO queue of floors per car. Riders press 5, 1, 9, 2 and the car zig-zags 5 → 1 → 9 → 2. Keep the stops in a sorted set plus a direction: the car goes 5 → 9, then 2 → 1 (or the reverse), never back and forth.

    5Working code

    Build bottom-up: Direction and Request, then Elevator, then the strategy, then ElevatorController. The code uses Lombok (@Getter, @Setter, @AllArgsConstructor) to remove boilerplate.

    5.1 Direction and Request

    enums/Direction.java · model/Request.java
    public enum Direction {
    UP, DOWN, IDLE
}

// A hall call: a person on a floor presses UP or DOWN
@Getter
@AllArgsConstructor
public class Request {
    private final int floor;
    private final Direction direction;
}

    A car call needs no class: it is just a floor for one known car. A hall call needs a direction, because the strategy prefers a car that already goes that way.

    5.2 Elevator — LOOK on a sorted set

    model/Elevator.java
    @Getter
public class Elevator {
    private final String id;
    private int currentFloor;
    private Direction direction = Direction.IDLE;
    private boolean doorsOpen;
    @Setter private boolean inService = true;
    private final TreeSet<Integer> stops = new TreeSet<>();

    public Elevator(String id, int startFloor) {
        this.id = id;
        this.currentFloor = startFloor;
    }

    public void addStop(int floor) {
        stops.add(floor);                                   // a set: pressing 7 twice = one stop
        if (direction == Direction.IDLE && floor != currentFloor) {
            direction = floor > currentFloor ? Direction.UP : Direction.DOWN;
        }
    }

    public boolean hasStops() { return !stops.isEmpty(); }

    // The farthest stop in the current direction: where this trip ends
    public int lastStop() {
        if (stops.isEmpty()) return currentFloor;
        return direction == Direction.DOWN ? stops.first() : stops.last();
    }

    // One tick = move one floor. LOOK: keep going while there are stops ahead, then turn.
    public void step() {
        doorsOpen = false;
        Integer target = nextStop();
        if (target == null) { direction = Direction.IDLE; return; }
        if (target == currentFloor) { stopHere(); return; }
        direction = target > currentFloor ? Direction.UP : Direction.DOWN;
        currentFloor += direction == Direction.UP ? 1 : -1;
        if (stops.contains(currentFloor)) stopHere();
    }

    private Integer nextStop() {
        Integer above = stops.ceiling(currentFloor);       // smallest stop >= floor
        Integer below = stops.floor(currentFloor);         // largest stop <= floor
        if (direction == Direction.UP && above != null) return above;
        if (direction == Direction.DOWN && below != null) return below;
        // Idle, or nothing left ahead: go to the nearest stop
        if (above == null) return below;
        if (below == null) return above;
        return above - currentFloor <= currentFloor - below ? above : below;
    }

    private void stopHere() {
        stops.remove(currentFloor);
        doorsOpen = true;
        if (stops.isEmpty()) direction = Direction.IDLE;
    }

    public String status() {
        String state = inService ? direction.name() : "OFF";
        return String.format("%s @%d %-4s %-10s %s", id, currentFloor, state, stops, doorsOpen ? "OPEN" : "    ");
    }
}

    Why a TreeSet? It keeps the floors sorted and unique. ceiling(f) gives the next stop above in O(log n); floor(f) the next one below. That is all LOOK needs: “next stop ahead, else turn”. Why direction is changed only in step() and addStop(): a new stop behind the car never flips it mid-trip, so riders already inside are not starved.

    5.3 SchedulingStrategy — which car?

    strategy/SchedulingStrategy.java · strategy/NearestElevatorStrategy.java
    public interface SchedulingStrategy {
    // Returns null when no elevator can take the request
    Elevator select(List<Elevator> elevators, Request request);
}

public class NearestElevatorStrategy implements SchedulingStrategy {

    @Override
    public Elevator select(List<Elevator> elevators, Request request) {
        return elevators.stream()
                .filter(Elevator::isInService)
                .min(Comparator.comparingInt(e -> cost(e, request)))
                .orElse(null);
    }

    // Floors the elevator must travel before it reaches the caller
    private int cost(Elevator e, Request r) {
        int here = e.getCurrentFloor();
        int target = r.getFloor();
        if (e.getDirection() == Direction.IDLE) return Math.abs(here - target);

        boolean onTheWay = e.getDirection() == r.getDirection()
                && (r.getDirection() == Direction.UP ? here <= target : here >= target);
        if (onTheWay) return Math.abs(here - target);

        // It must finish its trip first, then come back
        int end = e.lastStop();
        return Math.abs(here - end) + Math.abs(end - target);
    }
}

    Three cases. Idle: plain distance. Moving the same way and the caller is ahead: plain distance, it stops on the way. Otherwise: go to the end of the trip, then come back. Example: E1 goes UP from 0 to 4; a ▼ call on floor 2 costs E1 4 + 2 = 6, an idle E2 at 0 costs 2 → E2 wins. On a tie, min keeps the first car.

    5.4 ElevatorController — the entry point

    service/ElevatorController.java
    @Getter
public class ElevatorController {
    private static final int MAX_TICKS = 100;

    private final int topFloor;
    private final List<Elevator> elevators = new ArrayList<>();
    @Setter private SchedulingStrategy strategy;
    private int tick;

    // Floors are 0 .. floors - 1. All elevators start at floor 0.
    public ElevatorController(int floors, int elevatorCount, SchedulingStrategy strategy) {
        this.topFloor = floors - 1;
        this.strategy = strategy;
        for (int i = 1; i <= elevatorCount; i++) elevators.add(new Elevator("E" + i, 0));
    }

    // hall call: a person on a floor presses UP or DOWN
    public void requestElevator(int floor, Direction direction) {
        if (!isValidFloor(floor)) return;
        if (direction == Direction.IDLE
                || (floor == topFloor && direction == Direction.UP)
                || (floor == 0 && direction == Direction.DOWN)) {
            System.out.println("No " + direction + " button on floor " + floor + ".");
            return;
        }
        Elevator elevator = strategy.select(elevators, new Request(floor, direction));
        if (elevator == null) { System.out.println("No elevator available. Try again later."); return; }
        elevator.addStop(floor);
        System.out.println("Hall call " + floor + " " + direction + " -> " + elevator.getId());
    }

    // car call: a rider inside presses a floor button
    public void selectFloor(String elevatorId, int floor) {
        Elevator elevator = find(elevatorId);
        if (elevator == null || !isValidFloor(floor)) return;
        if (!elevator.isInService()) { System.out.println(elevatorId + " is out of service."); return; }
        elevator.addStop(floor);
        System.out.println("Inside " + elevatorId + ": floor " + floor);
    }

    // operator
    public void setMaintenance(String elevatorId, boolean on) {
        Elevator elevator = find(elevatorId);
        if (elevator == null) return;
        if (on && elevator.hasStops()) {
            System.out.println(elevatorId + " has stops left. Finish them first.");
            return;
        }
        elevator.setInService(!on);
        System.out.println(elevatorId + (on ? " out of service." : " back in service."));
    }

    // time: every elevator moves one floor per tick
    public void step() {
        tick++;
        elevators.forEach(Elevator::step);
        String line = elevators.stream().map(Elevator::status).collect(Collectors.joining(" | "));
        System.out.println(String.format("t%02d  %s", tick, line).stripTrailing());
    }

    public void runUntilIdle() {
        for (int i = 0; i < MAX_TICKS && elevators.stream().anyMatch(Elevator::hasStops); i++) step();
    }

    // find(id) prints "No elevator X." when missing; isValidFloor prints the range
}

    The controller is thin: validate, ask the strategy, call addStop. It never decides the order of stops. MAX_TICKS is a guard: a bug in step() cannot loop forever.

    5.5 Main — the client

    Main.java (part)
    ElevatorController building = new ElevatorController(10, 2, new NearestElevatorStrategy());

building.requestElevator(4, Direction.UP);     // -> E1 (tie, first car)
building.requestElevator(2, Direction.DOWN);   // -> E2 (E1 is going away)
building.runUntilIdle();

building.selectFloor("E1", 2);                 // E1 at 7: now going DOWN
building.selectFloor("E1", 9);                 // behind it: waits
building.selectFloor("E1", 5);                 // ahead: served first
building.runUntilIdle();                       // 5, 2, then turn for 9

    7Design patterns
    
  
    Be honest in the interview. Say which patterns the code uses and which ones you would add.
    
  
    
    
    Strategy used
    SchedulingStrategy + NearestElevatorStrategy. The controller holds the interface and can swap it at runtime with setStrategy.
    
    
    Central controller used
    ElevatorController is the one entry point. Cars do not talk to each other; the controller coordinates them (close to Mediator).
    
    
    Value object used
    Request is immutable: floor + direction. Safe to pass to any strategy.
    
    
    Tick simulation used
    step() moves time by one unit. The run is deterministic, so you can test it and replay it.
    
    
    State would add
    ElevatorState: Idle, Moving, DoorsOpen, Maintenance, Emergency. Worth it once doors take time or fire mode exists.
    
    
    Observer would add
    Floor displays and the app subscribe to “moved” and “doors open” events. Removes status() printing from the model.
    
    
    Command would add
    Each button press is a command in a queue. One controller thread runs them — the simple answer to concurrency.
    
    
    Singleton controller avoid
    Tempting (“one per building”), but it blocks tests and a second building. Create it once and pass it in.
    
  
    
  
    SOLID check
    
      
      
    • S — Controller: validate and route. Strategy: pick a car. Elevator: order and move.
      • 
      
    • O — A new dispatch rule is a new class. Direction-aware stops would edit Elevator — the known weak spot.
      • 
      
    • L — Any SchedulingStrategy works in the controller, as long as it returns an in-service car or null.
      • 
      
    • I — The strategy interface has one method.
      • 
      
    • D — The controller depends on the SchedulingStrategy interface, injected in the constructor.

    Example: a second strategy, swapped at runtime
    

    strategy/LeastBusyStrategy.java (would add)
    // Spread the load: the car with the fewest stops; ties go to the nearest
public class LeastBusyStrategy implements SchedulingStrategy {
    @Override
    public Elevator select(List<Elevator> elevators, Request request) {
        return elevators.stream()
                .filter(Elevator::isInService)
                .min(Comparator.comparingInt((Elevator e) -> e.getStops().size())
                        .thenComparingInt(e -> Math.abs(e.getCurrentFloor() - request.getFloor())))
                .orElse(null);
    }
}

// 9 am up-peak: change the rule, not the controller
building.setStrategy(new LeastBusyStrategy());

    8Similar problems
    
  
    A problem is similar only if the elevator model carries over: a controller gets requests, a strategy assigns each one to a moving worker, and each worker serves its own queue in a smart order along a line. The problems below share that skeleton. They are ranked by how much of this design you can reuse.
    

  
    The shared skeleton
    
    Controller → Strategy.select(workers, request) → worker.addStop(x) · each tick: worker.step() → next stop ahead, else turn.
    
  
    

  
    
    
    ProblemReuse from ElevatorNew part to learn
    
    
      
    Destination-dispatch elevators
    closest    		All of it: controller, strategy, Elevator.step(), LOOK.The rider types the target floor in the lobby. The strategy groups riders with the same target into one car, and the car gets two stops (pick-up + drop) at once.
    
      
    Disk arm scheduling (SCAN / LOOK / C-LOOK)TreeSet of positions, ceiling / floor, the exact nextStop() rule.One worker, no dispatch. Compare SCAN (go to the end), LOOK (turn at the last request) and C-LOOK (jump back, serve one way only). Measure total seek distance.
    
      
    Automated parking lift / car stackerA lift on a 1-D shaft, stops by level, maintenance mode, request queue.Each request is two moves (fetch a pallet, deliver it). Slots per level, so it mixes with Parking Lot.
    
      
    Warehouse shuttle / robot on a railController + strategy picks the nearest free robot; robot serves pick points in order along the rail.Load and capacity per trip; battery and charging as “out of service”.
    
      
    Cab / ride dispatch (Uber-style matching)Controller + Strategy.select(drivers, request) with a cost function; drivers can be offline.2-D distance instead of floors; ride lifecycle (requested → accepted → on trip); no LOOK order.
    
        
  
    

  
    Practice orderDisk scheduling (one worker, LOOK only) → Elevator (add dispatch) → Destination dispatch (smarter dispatch) → Parking lift (two-step requests) → Cab dispatch (2-D, lifecycle).
