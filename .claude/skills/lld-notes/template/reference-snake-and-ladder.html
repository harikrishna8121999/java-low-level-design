Design Snake and Ladder

Easy Java ~25 min read Code: org.nailyourinterview.lld.snakes_and_ladder

Snake and Ladder is a board game. Players take turns. Each player rolls a dice and moves forward. A ladder moves a player up. A snake moves a player down. The first player to reach the last cell wins.

This problem is a good first LLD. The rules are small, so you can focus on the method: find the entities, give each one a clear job, and connect them with the right relationships.

Every LLD answer follows the same 5 steps. Requirement gathering splits into 3 buckets: extensibility, dynamic input and high traffic. Click a step to jump to it.

    1.2 Core functional requirements

    • Create a square board of N cells, numbered 1…N in a zig-zag (serpentine) path.
    • Place snakes and ladders at random. No two obstacles share a start cell.
    • Support 2+ players. Each player starts on cell 1.
    • Players take turns in round-robin order.
    • A turn: roll the dice → move forward → if the cell has a snake or ladder, jump to its end.
    • If the roll goes past cell N, the player stays.
    • A player who lands exactly on N wins and leaves the turn order. The game ends when one player is left.

    1.4 Dynamic (user input)

    Nothing is hard-coded. The user gives the values at runtime. Main reads them with a Scanner and passes them to the Game constructor.

    • Board size (a perfect square, for example 100).
    • Number of players and their names.
    • Number of snakes, ladders and dice.
    Validate the inputSize must be a perfect square. Players ≥ 2. Snakes + ladders must fit on the board, or generateObstacles loops forever.

    1.5 High traffic (concurrency)

    Not needed here. One game runs in one thread. No resource is shared between users. Say this out loud, so the interviewer knows you checked.

    If they ask for an online version: a GameManager holds Map<gameId, Game>. Only the players of one game touch that game, so a lock per game is enough. No global lock.

    1.6 Non-functional requirements

    • Readable — each class has one clear job.
    • Testable — randomness must be replaceable in tests.
    Interview tipWrite the final requirements on the board, in these 4 buckets. Point to them when you justify a design choice later.

    2Core entities + breakdown

    Read the requirements again. Underline the nouns. Most nouns become classes. Verbs become methods.

    A game has a square board of cells. Some cells have a snake or a ladder. Players take turns. Each player rolls the dice and moves to a new position. A player who reaches the last cell wins.

    Snake and Ladder share one behavior: they move a player from a source cell to a destination cell. So we put them under one parent: Obstacle.

    EntityTypeResponsibility
    GameService / orchestratorOwns the board, dice and player queue. Runs the game loop. Decides the winner.
    BoardModelHolds the grid of cells. Maps a position to a cell. Places obstacles. Calculates the new position after a roll.
    CellModelOne square. Knows its number and its optional obstacle. Returns the final position for a player who lands on it.
    Obstacle (abstract)ModelHas src and dest. movePlayer() returns dest.
    Snake / LadderModelConcrete obstacles. Snake: head → tail (down). Ladder: bottom → top (up).
    PlayerModelName and current position.
    DiceModelRolls k dice and returns the sum.
    ObstacleTypeEnumSNAKE, LADDER.
    ObstacleFactoryFactoryCreates the correct obstacle from a type.
    Common mistakeDo not put the snake and ladder logic inside Game with if (isSnake) … else if (isLadder) …. The cell asks its obstacle. The obstacle answers. This is polymorphism.

    5Working code

    Build bottom-up: the small models first, then Board, then Game. The code uses Lombok (@Getter, @Setter, @RequiredArgsConstructor) to remove boilerplate.

    5.1 ObstacleType, Obstacle, Snake, Ladder

    enums/ObstacleType.java · model/Obstacle.java
    public enum ObstacleType {
    SNAKE,
    LADDER
}

@Getter
public abstract class Obstacle {
    protected int src;   // where the player lands
    protected int dest;  // where the player ends up

    public Obstacle(int src, int dest) {
        this.src = src;
        this.dest = dest;
    }

    public int movePlayer() {
        return dest;
    }

    public abstract ObstacleType getObstacleType();
}
    model/Snake.java · model/Ladder.java
    public class Snake extends Obstacle {
    public Snake(int head, int tail) {
        super(head, tail);          // src = head (high), dest = tail (low)
    }

    @Override
    public ObstacleType getObstacleType() {
        return ObstacleType.SNAKE;
    }
}

public class Ladder extends Obstacle {
    public Ladder(int top, int bottom) {
        super(bottom, top);         // src = bottom (low), dest = top (high)
    }

    @Override
    public ObstacleType getObstacleType() {
        return ObstacleType.LADDER;
    }
}

    Both constructors take (high, low). Each one maps it to (src, dest) in its own way. The caller does not need to know the direction.

    5.2 ObstacleFactory

    factory/ObstacleFactory.java
    public class ObstacleFactory {
    public static Obstacle createObstacle(ObstacleType type, int up, int down) {
        return switch (type) {
            case SNAKE -> new Snake(up, down);
            case LADDER -> new Ladder(up, down);
            default -> throw new IllegalArgumentException("Invalid obstacle type");
        };
    }
}

    One place knows how to build each obstacle. Game only says “give me a SNAKE from 54 to 34”.

    5.3 Player and Dice

    model/Player.java · model/Dice.java
    @Getter
@Setter
@RequiredArgsConstructor
public class Player {
    private final String name;
    private int position = 1;      // every player starts on cell 1
}

public class Dice {
    private final int noOfDices;
    private final Random random = new Random();

    public Dice(int noOfDices) {
        this.noOfDices = noOfDices;
    }

    public int roll() {
        int sum = 0;
        for (int i = 0; i < noOfDices; i++) {
            sum += random.nextInt(6) + 1;   // 1..6 per die
        }
        return sum;
    }
}

    5.4 Cell

    model/Cell.java
    @Getter
@Setter
@RequiredArgsConstructor
public class Cell {
    private final int position;
    private Obstacle obstacle;     // null when the cell is plain

    public boolean hasObstacle() {
        return obstacle != null;
    }

    public int getFinalPosition() {
        return hasObstacle() ? obstacle.movePlayer() : position;
    }
}

    Key idea. The cell answers “where does a player end up if they land here?”. No if snake / if ladder anywhere.

    Position → grid index (side length n):
    rowFromBottom = (p - 1) / n
    row = n - 1 - rowFromBottom
    offset = (p - 1) % n
    col = rowFromBottom % 2 == 0 ? offset : n - 1 - offset
    Shaded rows run right-to-left.
    model/Board.java
    @Getter
public class Board {
    private final int size;
    private final int sideLength;
    private final Cell[][] grid;

    public Board(int size) {
        this.size = size;
        this.sideLength = (int) Math.sqrt(size);
        this.grid = new Cell[sideLength][sideLength];

        int position = 1;
        boolean leftToRight = true;
        // fill from the bottom row up, flipping direction each row
        for (int i = sideLength - 1; i >= 0; i--) {
            if (leftToRight) {
                for (int j = 0; j < sideLength; j++) grid[i][j] = new Cell(position++);
            } else {
                for (int j = sideLength - 1; j >= 0; j--) grid[i][j] = new Cell(position++);
            }
            leftToRight = !leftToRight;
        }
    }

    private int getRow(int position) {
        int row = (position - 1) / sideLength;
        return sideLength - 1 - row;
    }

    private int getCol(int position) {
        int row = getRow(position);
        int col = (position - 1) % sideLength;
        return (row % 2 == 0) ? sideLength - 1 - col : col;   // ⚠ only correct for even sideLength
    }

    private Cell getCell(int position) {
        return grid[getRow(position)][getCol(position)];
    }

    public boolean addObstacle(Obstacle obstacle) {
        Cell srcCell = getCell(obstacle.getSrc());
        Cell destCell = getCell(obstacle.getDest());

        if (srcCell.hasObstacle() || destCell.hasObstacle()) {
            return false;                 // prevent overlapping obstacles
        }
        srcCell.setObstacle(obstacle);    // obstacle lives on its start cell
        return true;
    }

    public int getNewPosition(Player player, int offset) {
        int newPosition = player.getPosition() + offset;

        if (newPosition > size) {
            System.out.println("You are going out of the board! Better luck next time!");
            return player.getPosition();  // overshoot: stay in place
        }

        int finalPosition = getCell(newPosition).getFinalPosition();

        if (finalPosition < newPosition) {
            System.out.println("Oops! Snake has bitten " + player.getName());
        } else if (finalPosition > newPosition) {
            System.out.println("Congratulations! " + player.getName() + " moved up through a ladder");
        } else {
            System.out.println(player.getName() + " moved from " + player.getPosition() + " to " + newPosition);
        }
        return finalPosition;
    }

    public void printBoard(Queue<Player> players) { /* prints grid, 🐍 / 🪜 and player names */ }
}

    A 2D grid is optional. A flat Cell[size + 1] array indexed by position is simpler. Use the grid only if you need to print or draw the board. Say this trade-off out loud in the interview.

    5.6 Game — the orchestrator

    service/Game.java
    @Getter
public class Game {
    private final int noOfSnakes;
    private final int noOfLadders;
    private final Board board;
    private final Queue<Player> players;
    private final Dice dice;

    public Game(int size, int noOfLadders, int noOfSnakes, int noOfDice) {
        this.noOfSnakes = noOfSnakes;
        this.noOfLadders = noOfLadders;
        board = new Board(size);
        dice = new Dice(noOfDice);
        players = new ArrayDeque<>();
        initBoardObstacles();
    }

    private void initBoardObstacles() {
        generateObstacles(noOfSnakes, ObstacleType.SNAKE);
        generateObstacles(noOfLadders, ObstacleType.LADDER);
    }

    private void generateObstacles(int count, ObstacleType type) {
        Random random = new Random();
        int size = board.getSize();
        while (count > 0) {
            int up = random.nextInt(size - 1) + 2;    // 2..size
            int down = random.nextInt(up - 1) + 1;    // 1..up-1
            Obstacle obstacle = ObstacleFactory.createObstacle(type, up, down);
            if (board.addObstacle(obstacle)) {
                count--;                              // retry on clash
            }
        }
    }

    public void addPlayer(Player player) {
        players.add(player);
    }

    public void startGame() {
        board.printBoard(players);

        while (players.size() > 1) {
            Player currPlayer = players.poll();                 // front of the queue
            int diceRoll = dice.roll();
            int newPosition = board.getNewPosition(currPlayer, diceRoll);

            if (newPosition == currPlayer.getPosition()) {      // overshoot
                players.offer(currPlayer);
                continue;
            }
            currPlayer.setPosition(newPosition);

            if (newPosition == board.getSize()) {
                System.out.println(currPlayer.getName() + " has won the game!");
            } else {
                players.offer(currPlayer);                      // back of the queue
            }
            board.printBoard(players);
        }
    }
}

    7Design patterns
    
  
    Be honest in the interview. Say which patterns the code uses and which ones you would add.
    
  
    
    
    Simple Factory used
    ObstacleFactory.createObstacle(type, up, down) hides which constructor to call and how to map high/low to src/dest.
    
    
    Inheritance + polymorphism used
    Cell calls obstacle.movePlayer(). It does not care if it is a snake or a ladder.
    
    
    Composition used
    Game has-a Board, Board has-a Cell grid. Behavior comes from small parts, not deep hierarchies.
    
    
    Queue for round-robin used
    Not GoF, but key: poll() → play → offer(). A winner is simply not offered back.
    
    
    Strategy would add
    For dice, move rules and win policy. Swap behavior without editing Game.
    
    
    Observer would add
    Fire game events. Console, UI and tests subscribe. Removes System.out from the model.
    
    
    Builder would add
    new GameBuilder().size(100).snakes(8).ladders(7).dice(new NormalDice(1)).build()
    
    
    Singleton avoid
    Do not make Game or Board a singleton. You lose parallel games and clean tests.
    
  
    
  
    SOLID check
    
      
      
    • S — Cell knows its obstacle; Dice only rolls; Game only orchestrates. (Board’s printing breaks this.)
      • 
      
    • O — New obstacles need no change in Cell/Board/Game.
      • 
      
    • L — Any Obstacle subclass works where an Obstacle is expected.
      • 
      
    • D — Weak today: Game creates Dice itself. Inject it to fix.
      •

    8Similar problems
    
  
    A problem is similar only if the Snake and Ladder model carries over: a board of cells, players in a turn queue, and a game loop that moves, applies a cell rule and checks for a win. The problems below share that skeleton. They are ranked by how much of this design you can reuse.
    

  
    The shared skeleton
    
    Game → owns Board → owns Cells · Queue<Player> for turns · loop: get move → validate → apply → apply cell effect → check win → next player.
    
  
    

  
    
    
    ProblemReuse from Snake and LadderNew part to learn
    
    
      
    Ludo
    closest    		Dice, player queue, a numbered path of cells, overshoot rule, exact landing on home to win.Each player has 4 tokens and a different path. Capture (send a token home). Safe cells. A 6 to enter the board and for an extra turn.
    
      
    MonopolyDice, player queue, cells with an effect (like Obstacle): Property, Tax, Jail, Chance. Polymorphic cell.onLand(player).Circular board (wrap with % size). Money, ownership and rent. A player is out when bankrupt.
    
      
    Tic-Tac-ToeGame → Board → Cell grid, player queue, game loop, win check, Strategy for rules.Player chooses the cell (no dice). Validate an empty cell. Win check on rows, columns and diagonals. Draw when the board is full.
    
      
    Connect FourSame as Tic-Tac-Toe: grid, turn queue, loop, win check.A piece drops to the lowest free row in a column. Check 4 in a row in 4 directions.
    
      
    MinesweeperGrid of Cells, each with optional content (mine instead of obstacle). Random placement with clash check, like generateObstacles.Single player. Neighbour counts. Flood-fill (BFS) to reveal empty areas. Flags.
    
      
    BattleshipGrid of cells, random or manual placement with an overlap check, turn queue.Each player has a hidden board. Ships span many cells. Hit, miss and sunk states.
    
      
    ChessGame → Board → Cell grid, player queue, polymorphism (Piece subclasses, like Obstacle), Factory for pieces.Many move rules per piece. Check, checkmate and stalemate. Special moves (castling, en passant, promotion). The hardest one in this list.
    
        
  
    

  
    Practice orderTic-Tac-Toe → Ludo → Connect Four → Minesweeper → Chess. Each one adds one new idea to the same skeleton.
